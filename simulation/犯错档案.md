## 已记录错误

### 2026-07-26：直接运行 CTest，遗漏 catkin 的测试目标构建

- **现象**：WSL 中普通 `catkin_make` 成功，5 个 Python 测试通过，但 CTest
  报告找不到 `devel/lib/cym_planner/cym_planner_velocity_profile_test`。
- **原因**：`catkin_add_gtest` 注册了测试，却不会让普通 `catkin_make` 默认构建
  gtest 可执行文件；在执行 CTest 前没有先构建 `tests` 或 `run_tests` 目标。
- **修复**：先显式执行 `catkin_make tests`，确认测试二进制生成，再执行完整
  CTest 和 `catkin_test_results`。
- **预防**：含 `catkin_add_gtest` 的工作区验收统一使用“正常构建 → 测试目标构建
  → CTest/结果汇总”顺序；缺少测试二进制应归类为测试准备错误，而不是源码编译错误。

### 2026-07-26：把单分支克隆的 FETCH_HEAD 误当成远端跟踪引用

- **现象**：从 `yolo_cym1-local-mode` 同步规划器时，`git fetch origin
  yolo_cym1-local-mode` 成功，但随后使用
  `git restore --source=origin/yolo_cym1-local-mode` 报告无法解析引用。
- **原因**：目标工作区最初由 `--single-branch` 克隆，远端 fetch refspec
  不会为额外拉取的分支自动创建 `origin/yolo_cym1-local-mode` 跟踪引用；本次
  fetch 的提交只保存在 `FETCH_HEAD`。
- **修复**：确认 fetch 成功后改从 `FETCH_HEAD` 恢复明确的规划器目录，并用
  目录级差异检查确认与来源分支逐文件一致。
- **预防**：跨单分支工作区读取其他分支前先检查
  `git config --get-all remote.origin.fetch` 和 `git show-ref`；若只需要一次性
  读取，明确使用 `FETCH_HEAD`，若需长期跟踪则显式设置目标 refspec。

### 2026-07-26：视觉观察位只校验 XY，导致左中右朝向被跳过

- **现象**：车辆到达夹取区后看起来不再动作，最终没有夹取。现场日志实际显示
  左、中、右搜索都被调用，但中间观察位仅用 `0.4 s`、右侧仅用 `0.1 s`
  就被判定到达，随后食品被误识别为日用品，执行节点以
  `YOLOv5 could not find category food` 退出。
- **原因**：三个观察位的底盘位置很近、主要依靠不同朝向观察三块物品。
  左侧与中间目标的 XY 距离约为 `0.118 m`，小于原有 `0.12 m`
  位置容差；`position_only` 快捷完成条件完全忽略 yaw，因此车辆没有从左侧
  朝向依次旋转到中间和右侧，摄像头读到了错误区域。执行节点退出后准备仿真仍在，
  又把明确失败表现成了“停住”。
- **修复**：观察位完成条件同时校验 XY 和 yaw，yaw 容差设为 `0.12 rad`，
  并增加“XY 到达但相机朝向未到不得完成”、`±π` 环绕以及调用链回归测试。
  左→中→右搜索顺序保持不变；只有夹取完成后才切换增强激光避障。
- **预防**：所有面向传感器的导航目标都必须把朝向作为验收条件；若多个目标的
  XY 间距小于位置容差，测试必须覆盖“位置相同、朝向不同”的情况。任务节点
  FATAL 退出也必须读取 `/sim_task3/status` 或节点日志，不能只看 Gazebo 是否仍在。

### 2026-07-26：先猜测 `/cmd_vel` 争用，遗漏底盘低速死区

- **现象**：左、中、右识别已经正确，视觉节点持续输出 `-0.4 rad/s`，但画面中的
  目标位置和 `/odom` 朝向几乎不变，25 秒后视觉对准超时。最初把问题归因于
  `move_base` 与视觉节点共同发布 `/cmd_vel`，加入单发布者仲裁器后问题仍可复现。
- **原因**：没有先对“话题到达”和“物理执行”分层量测，就把合理的并发风险误当成
  已证实根因。空旷区域的受控实验显示，命令已由仲裁器以约 50 Hz 完整转发，但
  `0.40 rad/s` 和 `0.08 m/s` 都落在当前轮胎/接触模型的静摩擦死区内；导航规划器
  使用更大的控制量，所以巡线正常，而低速视觉伺服表现为完全不动。
- **修复**：保留单一 `/cmd_vel` 发布者以消除真实的控制源覆盖风险，同时按实测死区
  为视觉控制增加可配置下限：线速度 `0.15 m/s`、角速度 `1.30 rad/s`，并设置保守
  上限。完整实跑中视觉框从偏侧位置在约 4 秒内进入标定抓取范围。
- **预防**：控制链故障必须依次验证“源话题 → 仲裁输出 → `/odom` → 空旷场地不同
  幅值阶跃响应”；修复前先写能失败的死区回归测试。结构性改进不能替代根因证明，
  若第一次修复后原症状仍在，必须明确撤销原结论并继续诊断。

### 2026-07-26：夹取状态随关节回弹释放，终点又按精确泊车验收

- **现象**：日志显示真实夹取成功并切换增强避障，但运送到工厂附近后两次
  `move_base` 超时。现场同时出现 `grasp_attach` 跟随线程读取空偏移的异常；任务
  结束后状态已变为 `IDLE`，货物落在车辆/目标附近，而车辆距工厂中心约
  `0.24 m` 仍被判定失败。
- **原因**：夹取跟随器用实际夹爪关节位置大于阈值作为松爪条件，运输受力造成的
  瞬时回弹也会触发释放；跟随定时器和释放回调还会并发清空同一组偏移数据。
  另一方面，工厂本质是区域目标，任务却沿用了 `0.05 m + 最终 yaw` 的精确泊车
  成功条件，在锥桶和动态代价地图附近容易已经进入区域却无法收敛为 action 成功。
- **修复**：夹取后只响应明确的开爪控制命令，状态与跟随快照使用可重入锁保护；
  工厂到达改为夹取后专用的 `0.25 m` 位置区域验收，前半段观察位和规划参数不变。
  最终 WSL 实跑中货物保持 `GRASPING`，TCP 距离约 `0.023 m`，增强避障进入食品
  加工车间并发布 `DONE`。
- **预防**：抓取保持必须区分“控制意图”和“受力后的实际关节反馈”，跨线程状态要有
  原子快照或锁；任务测试不能停在“识别/夹取成功”，必须持续到货物跟随、模式切换、
  目标区域验收和 `DONE=true` 全部成立。

### 2026-07-26：只更新本地与 GitHub，导致 WSL 继续运行旧初始化代码

- **现象**：本地与 GitHub 已把 `direct_initial_configuration` 改为
  `false`，但用户在 WSL 启动后机械臂仍然竖直。
- **原因**：WSL 部署停在旧提交 `96f48a3`，其中
  `task3_prepare.launch` 仍明确传入 `direct_initial_configuration=true`。
  同步曾因未跟踪的本地 YOLO 资产而停止，但任务结束时没有消除该部署阻塞，
  也没有把“WSL 尚未更新”作为不可完成状态。用户的真实测试环境因此没有拿到
  已在本地验证的修复。
- **修复**：保留 WSL 本地资产并将其准确路径加入 `.git/info/exclude`，
  随后把 WSL 部署快进到与本地、GitHub 相同的提交，在用户 `car` 下重新构建，
  并通过 `/joint_states_full` 验收五个机械臂关节。
- **预防**：每次修改后强制执行“本地验证 → 提交推送 → WSL 快进 →
  WSL 构建/运行验证 → 三端 HEAD 核对”。只要 WSL 不一致，就不得宣告改动完成。

### 2026-07-27：用周期性 set_model_configuration 保持机械臂姿态导致行进中夹爪抖动

- **现象**：小车导航行进过程中机械爪持续抖动、机械臂模型乱飞；静止时完全正常。
- **原因**：`task3_prepare.launch` 传入 `hold_initial_arm_pose=true`，
  `set_arm_initial_pose.py` 因此以 30 Hz 调用 `/gazebo/set_model_configuration`。
  该服务内部会「暂停世界 → `SetJointPositions` 瞬移所有关节 → 恢复世界」，
  行进中每秒 30 次清空关节速度与接触状态，求解器每帧从与底盘动量矛盾的初值
  重启，关节数值发散；同时 `r_joint` 走 `gazebo_ros_control` 的
  `PositionJointInterface`（仓库未配置 `pid_gains`），即使 `gripper_controller`
  处于 stopped，`writeSim()` 仍每步把它拉向初始化命令 `0.0`，与 hold 写入的
  `1.0` 正面冲突，再由五个 mimic 插件逐帧放大到指节。碰撞或急停一叠加，
  `arm_joint5` 峰峰值达 3.03 rad、`r_joint` 达 1.90 rad 并越过 ±1.51 限位。
- **修复**：`task3_prepare.launch` 改为 `hold_initial_arm_pose=false`。
  同一 launch 的 `disable_arm_gravity=true` 已足够保持停放姿态；带加减速的
  前进/旋转/后退剖面实测 26 秒，每秒关节峰峰值不超过 0.008 rad，
  首尾漂移不超过 0.0002 rad。
- **预防**：控制器停用期间不得用 `/gazebo/set_model_configuration` 之类
  会暂停世界并重置物理状态的接口做周期性保持；只能用重力/阻尼等纯物理手段。
  新增此类「周期性写 Gazebo 状态」的逻辑前，必须先做运动状态下的关节峰峰值
  对照实测。

### 2026-07-27：把撞墙冲击当成行进抖动来度量

- **现象**：修复后重测仍出现关节大幅波动，一度误判修复无效。
- **原因**：探针脚本恒定发布 0.35 m/s 直行 15 秒，小车约 1.2 m 就撞上场景
  障碍并持续顶住；后续采样记录的是碰撞冲击与堵转，不是行进抖动。此外未重启
  仿真就连续复测，小车已停在障碍上，第二次测量整体无效。
- **修复**：改用带加减速的前进、原地旋转、后退组合剖面，并在报告中同时输出
  `base_footprint` 的 x 位移与逐秒峰峰值，确认底盘真在运动后才比较结论。
- **预防**：任何运动学对照实测都必须每次重启仿真，并先验证底盘实际位移，
  再解读关节数据；只看全程峰峰值会把一次碰撞放大成持续抖动的假象。

### 2026-07-27：固定关节建立后回写滞后的实际夹爪角导致立即释放

- **现象**：运行探针中固定关节服务报告成功连接物块，但约 `30 ms` 后又立即
  调用拆卸与动态物块恢复，表现为吸附仍然无法保持。
- **原因**：夹爪收到 `0.76` 闭合命令后，物理关节尚未收拢，实际反馈仍接近
  `1.0`。固定关节建立成功时，`grasp_attach.py` 又把这个滞后的实际角度发布到
  `/gripper_controller/command`；同一节点的命令回调把大于 `0.89` 的值视为明确
  开爪意图，从而自触发释放。
- **修复**：固定关节建立后不再回写实际关节角，保持调用方原始闭合命令；
  回归测试用“命令已闭合、反馈仍为开爪”的状态确认不会产生新的夹爪命令。
- **预防**：控制意图只能来自任务命令，不能用可能滞后的执行器反馈反向覆盖；
  所有吸附/释放状态机必须在实际 Gazebo 中核对服务时序，不能只依赖模拟单元测试。

### 2026-07-27：进程检查的 pgrep 模式匹配了检查命令自身

- **现象**：仿真已停止，部署前检查仍报告存在 `roslaunch` 进程并中止同步；
  输出中的唯一命中实际是正在执行检查的 `bash -lc` 命令。
- **原因**：使用 `pgrep -af "gzserver|roslaunch"` 时，完整正则文本也出现在当前
  shell 的命令行参数中，因此检查器匹配了自己。
- **修复**：精确进程名使用 `pgrep -x gzserver`，命令行模式使用
  `pgrep -f "[r]oslaunch"`，让正则仍能匹配目标却不以原样出现在检查命令中。
- **预防**：部署守卫的进程匹配必须先验证返回的 PID 与命令行，不能只根据
  `pgrep` 的退出码判定仿真残留。

### 2026-07-27：低速抬升通过后就采用固定关节，遗漏完整高速运输工况

- **现象**：TCP 与物块的固定关节在原地抬升探针中能稳定保持，但完整任务中
  小车一开始高速运输，物块和夹爪便出现乱飞。
- **原因**：验证只覆盖了低速机械臂抬升，没有覆盖运动学底盘的完整运输。
  底盘位姿快速改变时，ODE 要在 `0.01 s` 物理步内用固定关节约束追赶 TCP，
  约束反力又传回极轻的指节和机械腕。复跑测得载荷速度峰值 `6.84 m/s`、
  单帧跳变 `0.222 m`、相对 TCP 最大偏离 `0.122 m`。
- **修复**：删除后来增加的 Gazebo 固定关节系统插件，按官方
  `gazebo_ws.zip` 恢复由 `r_joint` 触发、100 Hz
  `/gazebo/set_model_state` 跟随的 `grasp_attach.py`。
- **预防**：载荷方案必须在同一次测试中覆盖“吸附、抬升、底盘加速、转弯、
  完整运输、释放”，并同时记录载荷速度、单帧位移和相对 TCP 偏差；原地探针
  只能作为初筛，不能作为稳定性结论。

### 2026-07-27：恢复官方配置时一度遗漏官方模型文件也已变化

- **现象**：最初只恢复官方 `grasp_attach.py` 和控制 YAML；随后发现当前
  URDF 仍有后加的 `<hasPID>`、指节阻尼、底盘惯量与传感器改动，world 的
  物理步长也从官方 `0.001 s` 改成了 `0.01 s`。这并不是“模型未改”状态。
- **原因**：把“不修改模型”误解为“保留当前已修改模型”，没有先把用户提供
  的 `gazebo_ws.zip` 当作唯一基准，对 URDF 和 world 做完整内容比较。
- **修复**：逐项恢复资源包中的 `car3.urdf` 和 `math.world`，撤销临时的
  mimic 插件兼容改法，并为两个官方文件加入忽略跨平台换行和文件末尾空行差异的
  SHA-256 回归测试。用户随后明确要求模型和 world 文件也必须保留官方原文，
  因此连资源包写死的 `/home/ucar/gazebo_ws` mesh URI 也恢复，不再在这两个
  文件内做 `model://` 路径兼容；路径适配必须在模型/world 之外处理。
- **预防**：“模型不允许修改”在本项目中表示必须与官方资源包一致。涉及控制
  回归时先验证官方 URDF/world 内容哈希，再检查脚本、插件和参数，不能用兼容
  代码掩盖模型基线已经漂移。

### 2026-07-27：PowerShell 提前展开了嵌套 Bash 命令中的变量

- **现象**：从 Windows 调用 `wsl.exe ... bash -lc` 做资源哈希和测试循环时，
  Bash 收到的 `$path`、`$test_file` 等变量已变为空，命令报
  `unexpected end of file`，一次还让 `unzip` 被 PowerShell 当作本机命令执行。
- **原因**：外层 PowerShell 使用双引号包住 Bash 脚本，反斜杠不能阻止
  PowerShell 展开 `$变量` 和 `$()`。
- **修复**：不再在嵌套命令里使用 Bash 变量循环；文件清单由 PowerShell
  `.NET ZipArchive` 只读比较，测试命令则展开为明确的文件列表。
- **预防**：PowerShell → WSL → Bash 的嵌套命令优先使用无变量的明确参数；
  必须传脚本时使用能被外层 shell 正确保护的引用方式，并先用无副作用短命令
  验证最终传入 Bash 的文本。

### 2026-07-27：恢复官方 world 后仍按墙钟等待机械臂轨迹

- **现象**：官方 `grasp_attach.py` 在实时 TCP 放置实验中能自动吸附，距离
  稳定在 `3.4–6.4 mm`；但完整任务两次都在物理夹取和官方兜底阶段失败，
  报告 TCP 框内没有物块。
- **原因**：官方 world 的 `max_step_size=0.001` 在当前机器上实时率约为
  `0.25`，而 `_move_arm()` 用墙钟等待轨迹的仿真时长。标称 2 秒的轨迹只运行
  约 0.5 秒仿真时间，任务便提前闭爪、抬升和执行兜底，TCP 实际尚未到位。
- **修复**：新增基于 `/clock` 的 `_wait_for_sim_duration()`；普通机械臂轨迹、
  带腕部碰撞保护的下探轨迹和保护后的回退轨迹都等待足够的仿真时间。
- **预防**：Gazebo 中 `JointTrajectoryPoint.time_from_start` 属于仿真时间；
  任何后续动作都必须以 `/clock` 或到位反馈为前置条件，不能假设 RTF 为 1
  后直接用墙钟 `sleep`。

### 2026-08-10：官方吸附路径收臂与导航并发，机械臂被误判为障碍物

- **现象**：夹取物品后车辆一边抬臂一边起步，抬臂过程中伸出的机械臂被激光
  雷达扫成障碍物，干扰后续路径规划与避障。
- **原因**：`_pick()` 官方吸附路径在吸附确认后只非阻塞发布收臂轨迹
  （`_publish_arm_target()`）就立即切换 `laser_avoidance` 并启动 `move_base`；
  纯物理夹取路径使用阻塞 `_move_arm()`，因此只有默认启用的官方吸附路径暴露
  该问题。
- **修复**：官方吸附路径收臂改为阻塞 `_move_arm()`，等待携带位轨迹完成后再
  切换导航模式并发布 `carry_mode=True`；两条路径统一为「抬完臂再跑」，状态
  文案同步更新；并发测试重命名为 `test_task3_carry_sequence.py` 并改为顺序
  断言。
- **预防**：夹取成功后任何会改变车体轮廓的动作（抬臂、伸缩等）都必须等待
  完成或停在车体包络内再启动导航；引入“并行执行”优化时，先检查动作过程中
  的传感器是否会把自己误判为障碍物。

### 2026-08-11：收臂完成后保留全局代价地图激光残影

- **现象**：夹取过程中物块被雷达短暂扫到并写入全局代价地图。物块随后随夹爪
  移动，新的激光射线被物块本身截断，旧的 map 坐标障碍格无法被射线清除，导致
  去工厂的路径被持续堵住。
- **原因**：上一轮修复只保证收臂完成后才启动导航，却未清除收臂阶段已经写入
  非滚动全局地图的动态障碍残影；已有 `clear_costmaps` 调用只位于导航超时重试
  路径，正常夹取成功后不会执行。
- **修复**：在两种夹取路径共用的收臂完成边界调用 `/move_base/clear_costmaps`，
  然后才切换 `laser_avoidance` 和发布携带模式；回归测试锁定“收臂 → 清图 →
  导航”的顺序。
- **预防**：动态物体从传感器视场进入车体携带包络时，必须在其处于传感器安全
  姿势后主动清除全局动态层，再启动依赖该地图的导航；不能假设后续命中会反向
  清除历史 map 坐标。
