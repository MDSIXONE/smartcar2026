# 常见问题

## Gazebo 和 RViz 窗口出现 `[WARN:COPY MODE]`，画面无法正常显示

### 现象

- Windows 窗口标题变为 `[WARN:COPY MODE] Gazebo` 或
  `[WARN:COPY MODE] ... RViz`。
- `gzclient`、RViz、`gzserver` 和 `move_base` 进程仍然存在，但窗口空白、
  刷新缓慢或无法正常交互。
- ROS 日志中通常搜索不到 `COPY MODE`，因为该前缀由 Windows 侧的 WSLg
  RDP 客户端添加，不是 Gazebo、RViz 或 ROS 发出的警告。

### 根因

这是 WSLg 图形共享通道初始化失败，不是 CymPlanner、代价地图或 Gazebo
场景配置错误。故障现场的 `/mnt/wslg/weston.log` 会同时出现类似内容：

```text
rdp_allocate_shared_memory: Failed to open "/mnt/shared_memory/{...}" with error: Input/output error
RDP backend: use_gfxredir = 0
```

此时 WSLg 期望使用的 `/mnt/shared_memory` 没有挂载为 Windows/WSLg
共享内存通道，而是落在发行版普通根文件系统中。Weston 因而关闭
GFX/VAIL 重定向，退回逐帧复制的 COPY MODE。Gazebo 和 RViz 会同时受影响。

即使 RViz 使用了 `LIBGL_ALWAYS_SOFTWARE=1`，它也不是本故障的根因：
未设置该变量的 Gazebo 同样进入 COPY MODE；同时 `glxinfo -B` 仍可显示
D3D12 硬件加速可用。微软公开的
[WSLg #972](https://github.com/microsoft/wslg/issues/972) 记录了相同的窗口标题、
共享内存错误和界面异常。

### 快速确认

在非 root 用户 `car` 下运行：

```bash
grep -E "rdp_allocate_shared_memory|use_gfxredir" /mnt/wslg/weston.log
findmnt /mnt/shared_memory
glxinfo -B
```

若第一条显示共享内存 `Input/output error` 和 `use_gfxredir = 0`，同时第二条
没有输出挂载信息，即可确认是 WSLg COPY MODE。不要通过反复修改 RViz、
Gazebo 或规划器参数来处理。

### 恢复顺序

先保存工作并停止当前仿真。随后在 Windows PowerShell 中按最小影响顺序执行：

```powershell
wsl --terminate Ubuntu-20.04
```

重新进入 Ubuntu 并启动一个 GUI 程序检查窗口标题。如果仍有
`[WARN:COPY MODE]`，再执行：

```powershell
wsl --shutdown
```

`wsl --shutdown` 会停止所有 WSL 发行版，也可能中断 Docker Desktop，
执行前必须确认其他 WSL 工作已经保存。恢复后重新检查 Weston 日志；
窗口标题不应再有 COPY MODE，`/mnt/shared_memory` 应恢复共享通道。

### 本次犯错与预防

本次验证只覆盖了 `gui:=false rviz:=false` 的无界面路径，证明了仿真、机械臂
和规划器可运行，却没有覆盖 WSLg 窗口传输链路。因此“无界面仿真通过”不能
推导出“Gazebo/RViz 界面正常”。

第二个漏点是最初只搜索 `.ros/log`。`[WARN:COPY MODE]` 属于 Windows/WSLg
窗口层信号，正确取证位置是 Windows 窗口标题和
`/mnt/wslg/weston.log`。今后的 GUI 验证必须同时检查：

1. Gazebo 和 RViz 窗口标题没有 `[WARN:COPY MODE]`；
2. Weston 没有 `rdp_allocate_shared_memory` 错误；
3. `/mnt/shared_memory` 共享通道正常；
4. 再检查 Gazebo/RViz 自身渲染和 ROS 数据。

## 后半段低速停车时车头前倾，前半段高速急停却不会

### 根因

这不是单纯的制动惯性。故障时车体俯仰角增大的同时，底盘高度也会上升，
说明车轮或底盘已经接触并爬上锥桶、墙体等碰撞体。后半段增强激光轨迹
规划器曾绕过前半段 `main_legacy` 使用的代价地图硬边界，只用较短时间窗内
的激光几何轨迹判定安全，因此会接受净空很小但尚未几何相交的贴边轨迹。
载货后的质量和质心变化会放大接触后的俯仰，但不是首次前倾的原因。

### 本次犯错与预防

曾把问题优先归因于速度突变，并尝试线性减速。这只能改变碰撞发生的速度，
不能阻止车辆继续进入障碍物；减速距离还可能让车更深入障碍区。

最终没有继续修补增强轨迹采样器。取货前后改为复用完全相同的 origin/main
巡线控制律，仅替换判障来源：取货前沿路径检查 costmap，取货后直接读取
`/scan`，沿前视路径密集投影完整矩形车体；任一激光点落入投影才返回
`false`，交给 `move_base` 重新规划。这样速度、转向和巡线行为不再因任务
阶段变化，升级范围只限于官方要求的雷达碰撞输入。遇到类似问题应先核对
俯仰角、底盘高度、障碍距离和规划器安全状态，不要先修改 URDF、世界模型
或反复调整减速度。

## 夹取成功后物块突然消失

曾有一版 `grasp_attach` 会删除动态 `cube_N`，再生成无碰撞的可视载荷。
Gazebo 的删除服务先返回、world 后更新，删除和生成之间存在竞态，可能把
刚生成的载荷一并删掉。

当前已恢复官方实现：夹取和释放期间不删除、不重生、也不改名物块，只在吸附
状态下更新原 `cube_N` 的位姿，因此这条删除/生成竞态不再存在。

## 物块到达视觉目标后，RViz 的 YOLO 图像停止刷新

原实现只在搜索、对准和分类代码主动调用 `_detect()` 时发布
`/sim_task3/vision/debug_image`。目标确认后任务进入机械臂和导航阶段，
相机订阅仍在接收新图像，但没有代码继续运行检测与发布，所以 RViz 保留的是
最后一帧，并不是摄像头或 RViz 断流。

现在第一次正常检测后会启用独立的低频视觉心跳；主视觉循环工作时由主循环
发布，离开视觉循环后由心跳处理最新帧。ONNX 推理由互斥锁串行化，避免两个
线程同时使用检测会话。心跳不会在实时率预检期间启动，以免额外 CPU 负载
干扰启动判定。

## 正常夹取姿态可用，但物块仍被吸附并在高速行驶时拖后

旧逻辑把“夹爪关节小于闭合阈值且物块靠近 TCP”直接当成吸附条件，并以
100 Hz 循环调用 `/gazebo/get_link_state` 和 `/gazebo/set_model_state`。
历史实现每次还把载荷速度清零，因此物块会在两次服务之间停住，再跳到新的
TCP 位置；提高定时器频率只会增加服务排队，不能消除逐帧移动。

曾尝试把可视载荷改为动态模型并创建 TCP 固定关节。这在低速抬臂探针中稳定，
但完整运输时底盘是运动学高速移动，ODE 必须在每个 `0.01 s` 物理步内用约束
追赶 TCP。现场复跑中载荷速度峰值达到 `6.84 m/s`、单帧跳变 `0.222 m`，
相对 TCP 最大偏离 `0.122 m`，还会把约束反力传回极轻的指节和机械腕，因此
出现“物块乱飞”。提高 ROS 跟随定时器频率不能解决这个问题：物理世界本身
只有 100 Hz，更高频率只会重复排队服务请求。

对照官方提供的 `gazebo_ws.zip` 后，最终恢复官方机制：`grasp_attach.py`
监视 `/joint_states` 的 `r_joint`，实际角度低于 `0.8` 且物块中心进入 TCP
的 `±0.02 m` 框时自动吸附；随后以官方默认 100 Hz 读取 TCP 并调用
`/gazebo/set_model_state`。明确发布大于 `0.89` 的开爪命令时停止跟随；
运输冲击造成的短暂关节回弹不能释放载荷。后来增加的
Gazebo 吸附插件和六组夹爪 `gazebo_ros_control/pid_gains` 已删除，控制配置
恢复当前项目值。`car3.urdf` 用内容哈希回归测试锁定，不得修改；`math.world`
的模型部分同样锁定，只有 `<physics>` 段的时间参数由负责人授权可按需调整
（见 `docs/changes/`，当前物理步长已设为 200 Hz），调整后必须同步更新
world 哈希回归与 `test_world_uses_200hz_physics_step`。2026-07-27 重新与用户
提供的 `gazebo_ws` 对照后，`math.world` 一致，但当前 URDF 仍有惯量、阻尼、
轮面接触和相机参数差异；正式发布前必须由负责人决定是否解除“禁止修改 URDF”
约束并恢复，不能继续把当前 URDF 表述为官方文件完全一致。
官方 world 中写死的 `/home/ucar/gazebo_ws` 场区挂牌 URI
在当前 WSL 不存在；为保持 `math.world` 模型部分原文不变，启动时
`scene_sign_compat.py` 只在旧绝对路径不可用时，通过 `model://` 加载同一份
官方 OBJ 作为无碰撞可视覆盖层。旧路径可用时该节点不做任何替换。

官方 world 原本使用 `max_step_size=0.001`、`real_time_update_rate=1000`，
官方跟随器是 100 Hz；该组参数在当前机器上的实时率约为 `0.25`，仿真时间
明显慢于墙钟。负责人授权后，`<physics>` 段调整为 333 Hz 物理步长
（`max_step_size=0.003`、`real_time_update_rate=200`，200 步 × 0.003 s =
0.6 s 仿真时间/实时秒，实时率约 0.6）：计算负载为官方的 1/5，实测 200 Hz
步长 + RTF 1.0 时任务速度过快曾导致翻车，故收细步长（更稳）并把实时率
钳制在 0.6 左右。机械臂轨迹等待逻辑仍按 `/clock` 仿真时间执行不受影响。
如需恢复官方数值，改回 `0.001/1000` 并同步更新上述两个回归测试。
当前任务仍保留 `/grasp_attach/attach` 和 `check_physical` 兼容接口，识别、
导航和失败重试不需要退回官方旧任务流程；实际吸附与跟随则使用官方实现。
`task3_execute.launch` 的 `attachment_fallback_enabled` 和
`task3_prepare.launch` 的 `grasp_attachment_enabled` 默认同时启用，显式关闭
时仍可进行纯物理夹持试验。

## 机械臂下探接近物块时，夹爪突然出现多余旋转

五个关节的下探命令中 `arm_joint5` 始终为 `0`。50Hz 现场记录显示，控制器
接管和前段下探期间 `arm_joint5` 与夹爪开度均保持稳定；接近最低点继续推压
后，`arm_joint5` 才从约 `0` 突然被外力扭转，旧流程中最大达到
`-6.83 rad`，夹爪关节也同时越过物理限位。这是末端接触后仍继续下压造成的
Gazebo 物理失稳，不是轨迹主动命令腕部旋转。

现在抓取下探会以 `0.035 rad` 为腕部偏转保护阈值，并保留最近六个稳定关节
样本。一旦接触开始扭动腕部，立即停止原下探目标，退回最近稳定接近姿态后
闭爪。短扰动回归中腕部最大偏转为 `0.038 rad`，随后恢复到
`0.00007 rad`。当前默认官方吸附路径也不执行曾用于判定兜底条件的
“抬升 20% 后检查”动作，而是下探后单次闭爪并直接抬到携带位。
吸附服务确认成功后，任务会先等待机械臂完全恢复到携带姿势，再开始向目标
车间导航；抬臂完成前底盘不会移动，避免收臂过程中的机械臂被激光雷达误判
为障碍物。

## 执行 `task3_execute.launch` 后节点很快退出，看起来没有运行

检查 `~/.ros/log/latest/task3_pick_deliver-1.log`。如果末尾是
`RTF preflight failed`，说明任务代码在真正开始巡航前主动退出，并非
机械臂保护、YOLO 或规划器启动失败。本次连续两次现场值分别为 `0.9280`
和 `0.9320`，低于旧的硬门槛 `0.950`。

旧设计把五秒实时率采样同时当作性能提示和功能启动条件。在 WSLg 中同时开启
Gazebo GUI、RViz 和 YOLO 时，渲染负载会让 RTF 在门槛附近波动；即使节点、
话题、服务和规划器都已经正常连接，一次低采样仍会抛出异常并结束整个任务。
这是“界面正常但执行命令没反应”的直接原因。腕关节监测订阅已经正常建立，
日志中没有它引起的异常。

现在使用 `rtf_minimum: 0.30` 作为当前本机流程的性能目标，并保持
`rtf_preflight_strict: false`：低于目标时在终端和任务状态话题发布警告，
随后继续运行。只有需要严格比赛计时验收时才将该参数设为 `true`。今后不能
仅凭节点退出表象猜测最近的功能改动；应先读取节点日志，并把性能前检与功能
可用性分开设计。

## 识别物块后的视觉对准为什么会旋转车身

旧视觉伺服把检测框的水平误差写入 `Twist.angular.z`，目标短暂丢失时也通过
角速度向最后一次出现的方向搜索，因此从观察位接近物块时会改变车头方向。
这会让机械臂相对货架的抓取朝向不再固定。

现在视觉对准阶段不再写入角速度：水平误差映射到 `Twist.linear.y` 做左右
平移；横向误差进入允许范围后，再用 `Twist.linear.x` 前进或后退调节距离。
短暂丢失目标时同样只沿左右方向搜索。观察位之间的正常导航仍可转向，但从
识别到物块、切换到视觉伺服开始，车头朝向保持不变。

## 没有识别到物块或夹取失败后任务直接结束

旧任务把“左、中、右均未确认目标”和“默认物理夹取完成”都当成一次性流程：
三处识别均失败时直接抛异常；吸附关闭后又跳过了物理保持检查，因此夹空也会
错误进入运输阶段。这两个出口都没有回到视觉搜索。

现在识别使用完整循环：先在同一 XY 按左侧、顺时针 90°上方、再顺时针
90°右侧扫描；三个方向都未确认时，再到旧版左、中、右三组独立观察位复查。
两阶段都失败才从旋转搜索重新开始，直到确认目标或 ROS 被主动关闭。默认启用
官方吸附时，夹取只执行一次“下探、把目标对齐 TCP、闭爪、吸附”；吸附确认后
下发携带姿势并同时开始底盘导航，不再先做物理试夹、20% 探测抬升、失败回落
和第二次闭爪。

若显式关闭吸附，任务才使用纯物理夹爪路径：闭爪后直接抬到携带位，并检查
物块是否仍在夹爪中。物理检查失败时，车辆停止、夹爪张开、机械臂恢复
`task3_prepare.launch` 发布的 `arm_start_pose`，然后重新执行视觉识别与
对准。只有所选夹取路径成功后才切换载货雷达避障并前往目标区域。为保证
“直到成功”，145 秒任务预算默认只发布一次性能警告，不终止重试；严格计时
验收时可显式设置 `task_wall_budget_strict: true`。

## 爪子已经碰到物块，但没有夹起且机械臂模型一直飘

50Hz 同步记录机械臂关节、TCP 和物块位姿后确认，这里至少有两个独立问题：
第一次夹取时物块高度仍保持在地面附近；物理检查失败并恢复初始姿态后，
代码又让机械臂和夹爪控制器在下一轮导航期间继续运行。后者会把夹爪接触控制
的轻微抖动与底盘运动叠加，形成整套机械臂乱飞。重试导航前必须像首次巡航
一样停止这两个控制器，并恢复无控制器的初始姿态保持。

诊断期间还发现 Gazebo 会用多圈累计值报告同一个 revolute 关节姿态，例如
`-6.78 rad` 与 `-0.50 rad` 等价。曾错误地把所有控制目标强制归一到
`[-pi, pi]`；当当前反馈停留在多圈分支时，这反而会把小幅姿态变化变成跨越
数圈的轨迹。正确做法是以当前反馈为基准，用
`current + atan2(sin(target-current), cos(target-current))` 选择最近的
等价目标。回归测试覆盖正负多圈反馈，确保目标与期望姿态等价且离当前反馈
不超过半圈。

因此不能只凭单次“角度超过 pi”就判定命令越界，也不能把视觉上的飞散统称
为吸附或惯性问题。应同步检查仿真实时倍率、控制器运行状态、关节等价角、
TCP/物块距离和物块高度，再区分接触抖动的触发因素与错误轨迹、错误控制器
生命周期造成的放大因素。

## 小车行进过程中机械爪一直抖动

静止时正常、一开始移动就抖，说明问题出在行进期间对 Gazebo 的周期性写入。
`task3_prepare.launch` 曾传入 `hold_initial_arm_pose=true`，
`set_arm_initial_pose.py` 会以 30 Hz 调用 `/gazebo/set_model_configuration`
保持停放姿态。该服务内部先暂停世界，再用 `SetJointPositions` 瞬移全部关节，
然后恢复世界，等于每秒 30 次清空关节速度和接触状态。行进中底盘动量与被清零
的关节状态互相矛盾，求解器每帧从矛盾初值重启，关节数值迅速发散。夹爪
`r_joint` 使用 `PositionJointInterface` 且仓库未配置 `gazebo_ros_control`
的 `pid_gains`，即使 `gripper_controller` 处于 stopped，`writeSim()` 仍每个
物理步把它写向初始化命令 `0.0`，与保持逻辑写入的 `1.0` 直接冲突，再经五个
mimic 插件逐帧放大到指节，于是肉眼看到持续抖动。

修复方式是把 `hold_initial_arm_pose` 设为 `false`。同一 launch 里的
`disable_arm_gravity=true` 已经用纯物理方式托住停放姿态，无需周期性写入。
用带加减速的前进、原地旋转、后退组合剖面实测约 26 秒：关闭后每秒关节峰峰值
始终不超过 0.008 rad，全程首尾漂移不超过 0.0002 rad；保持开启时同一剖面
虽也能收敛，但一旦叠加碰撞或急停，`arm_joint5` 峰峰值达 3.03 rad、
`r_joint` 达 1.90 rad 并越过 ±1.51 限位，`r_link` 高度掉落 0.19 m。

注意判读实测数据时必须确认底盘确实在动：若探针只发 0.35 m/s 直行，小车会在
约 1.2 m 处撞上场景障碍，此后测到的是碰撞冲击而非行进抖动，两种情况的结论
完全不同。每次对照都要重启仿真并检查 `base_footprint` 的 x 位移。

控制器停用期间保持姿态只能依靠重力、阻尼这类物理手段，不能使用会暂停世界
并重置物理状态的服务接口。
