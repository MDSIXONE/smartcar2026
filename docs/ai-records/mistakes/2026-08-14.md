# 2026-08-14 错误记录

### 2026-08-14：误把讯飞麦克风阵列当成普通外设拔掉（语音唤醒硬件识别）

- **现象**：为整改 USB 共 Hub 问题让用户拔掉扬声器，用户"全部拔掉"后把麦克风阵列也拔了；复查 dmesg 无新 disconnect 事件、lsusb 拓扑不变，才发现拔错了设备。
- **原因**：不认得硬件身份——讯飞环形六麦阵列走**私有 USB HID 协议**（不是 ALSA 声卡，`arecord` 读不到），VID:PID 为 `10d6:b003`（Actions）；USB 扬声器 UACDemoV1.0 是 `001f:0b21`（ALSA card 名 `UACDemoV10`，见 `/home/ucar/wake/audio_dev.py` 的 `CARD_NAMES`）。权威依据是车端 `/home/ucar/wake/micarray/res/xf_mic.rules`（`10d6/b003`）。
- **处理**：把麦克风阵列和扬声器都插回（物理限制只能共 Hub）；mission 语音唤醒靠麦阵列、播报靠扬声器，缺一不可。
- **预防**：动 USB 设备前先 `lsusb` 并与 `xf_mic.rules`、`audio_dev.py` 的 CARD_NAMES 对照，明确每个设备的身份再操作；"拔掉扬声器"必须指明是 `001f:0b21` 那根 USB 线。

### 2026-08-14：等仿真期间 odom 断流导致任务 ABORTED（共 Hub 扰动）

- **现象**：mission 跑到 `SIMULATION_WAIT_DONE`，小车静止等仿真时 16:22:06 任务 `ABORTED "Odom sensor not active any more"`（bridge 16:22:20 才 `SIMULATION_BRIDGE_DONE`，任务先死）。
- **原因**：同一 Terminus Hub 上的麦阵列（`1-2.1`）16:21:42 断连重连，扰动同 Hub 的 CP2102 串口（`1-2.2`），odom 静默 >4s → `robot_pose_ekf`（`sensor_timeout=4.0`，见 `ucar_bringup.launch` 注释）打印 `Odom sensor not active any more` → 任务 `rosout_cb` 按关键字捕获 → `critical_error` → 下一轮 `require_safe`（`simulation_wait_done` 每轮调用）abort。dmesg -T 时间线（16:21:42 disconnect / 16:21:47 re-enumerate）与任务日志对拍确认。
- **处理**：`stop_2026_task.sh` 停任务；物理整改方向是扬声器/麦阵列不与 CP2102 共 Hub（operations.md §6 早已警告）；若物理只能共 Hub，软件侧需同步提高 `robot_pose_ekf sensor_timeout` 与任务 `odom_timeout`/`tf_timeout`（覆盖约 5 秒的 USB 重枚举窗口），本次未实施即重跑。
- **预防**：跑 mission 前 `lsusb -t` 确认 CP2102 与音频/麦阵列不共 Hub；等仿真期间 odom 断流先查 `dmesg -T | grep disconnect` 时间线再下结论。

### 2026-08-14：bridge 单轮服务 + 仿真世界不重置导致重跑失效

- **现象**：上一轮仿真 done 后重跑主流程，bridge `/status` 仍是 `done`（耳机/电子产品），Gazebo 世界处于上一轮完成态。
- **原因**：`sim_bridge.py` 每次只服务一轮，done 后 `POST /start` 返回 409（文档 §9 已写明需重启 bridge）；task3_prepare 的 spawn 物品被上一轮任务取走，世界不重置新一轮会找不到物品。
- **处理**：`kill -INT` bridge 进程重开 D tab；`kill -INT` task3_prepare 的 roslaunch 进程树（约 9x2s 退出）重开 C tab 重置世界；确认 `/map` 就绪 + bridge `waiting` 后再跑小车流程。
- **预防**：重跑主流程前三步固定为：重置仿真世界（重启 prepare）→ 重启 bridge 到 waiting → 小车 check/manual/mission。

### 2026-08-14：`~/.ros/log/latest` 软链与车端时钟不可信

- **现象**：检查 manual 串口错误时 grep `latest` 匹配到的是 16:22 旧 mission 的 `sensor not active` 日志；某 run 目录 mtime 显示 2029 年。
- **原因**：`latest` 软链可能指向旧 run 目录（ROS 工具日志也会写入 latest 指向的目录）；车端系统时钟漂移导致 mtime 异常。
- **处理**：判断日志新旧按**内容内的时间戳**（`[rosout] 2026-08-14 HH:MM:SS`），不信任 `latest` 软链与文件 mtime；用 `pgrep -af roslaunch ucar_2026` 确认当前 launch PID 后再定位其日志。
- **预防**：查车端日志先 grep 内容时间戳定位目标时间段；`latest` 仅作参考路径。

### 2026-08-14：timeout 退出码导致安全检查脚本 `_FAIL` 误报

- **现象**：check_safety 输出 `TF_ODOM_BASE_FAIL`/`TF_MAP_BASE_FAIL`/`SCAN_HZ_FAIL`，实际 odom/TF/scan 数据全部正常。
- **原因**：`timeout 8 rosrun tf tf_echo ...` 持续输出直到 timeout 杀掉进程，退出码非零触发 `|| echo ..._FAIL`；长驻命令被 timeout 截断是预期行为。
- **处理**：按输出内容判断（odom 数值有限、tf 连续多帧、scan 平均频率 ~12Hz），忽略 timeout 退出码。
- **预防**：脚本里长驻命令用 timeout 截断时，不要在 `||` 分支打 FAIL——要么检查输出内容，要么用退出码 124（timeout 特有）单独区分。

### 2026-08-14：COPY MODE 预检时机太早，GUI 启动后仍退化

- **现象**：预检在启动终端 A/B 之前做（`wsl --shutdown` 后），显示通过；但终端 C（Gazebo/RViz）启动后 WSLg 落回 COPY MODE（weston.log 重新出现 `use_gfxredir = 0`）。
- **原因**：预检做太早，GUI 启动过程本身可能触发 WSLg 退化；A/B 是 headless 进程不代表 C 安全。
- **处理**：`wsl --shutdown` 重来（`wsl --terminate` 无效，08-10 教训），严格按 A → B → **预检** → C → D 顺序，且 C 启动后等 `/map` 就绪时**再复检一次** weston.log 才继续。
- **预防**：预检必须在启动 GUI 前一刻做；GUI 起来后（等 /map 期间）复检一次才算过关。

### 2026-08-14：SCP 多文件目标目录遗漏子路径，文件误落包根目录

- **现象**：同时上传 `scripts/start_2026.sh` 与 `launch/2026.launch` 时，SCP 目标写成包根目录，生成了不会被 ROS 使用的 `~/ucar_ws/src/ucar_2026/start_2026.sh` 和 `2026.launch`，实际运行文件尚未更新。
- **原因**：SCP 多源复制到同一个目录只保留文件名，不会自动保留本地的 `scripts/`、`launch/` 层级。
- **处理**：先按绝对路径核对误放副本与实际运行文件，删除两份已确认的误放副本；随后逐文件上传到准确的远端子目录，并以 SHA-256 对比确认。
- **预防**：部署跨子目录文件时，为每个源文件指定完整远端目标路径；上传后先核对目标路径和 SHA-256，再宣称部署完成。

### 2026-08-14：catkin_test_results 不能合并多个结果目录

- **现象**：lane_proto 与 ucar_2026 的 `run_tests` 已执行完成，但将两个 `build/test_results/...` 目录一起传给 `catkin_test_results` 时命令报 `unrecognized arguments`。
- **原因**：该 CLI 只接受一个可选结果目录位置参数，不支持一次汇总多个目录。
- **处理**：分别执行 `catkin_test_results --verbose build/test_results/lane_proto` 与 `catkin_test_results --verbose build/test_results/ucar_2026`，均为 0 errors / 0 failures。
- **预防**：多包回归后按包分别调用结果工具，或不传路径读取工作区总目录；不要把多个子目录并列传入。

### 2026-08-14：bridge stdout pipe 失效使 HTTP 状态连接空响应

- **现象**：小车 `/status` 轮询报 `No status line received - the server has closed the connection`，bridge 进程仍在且端口仍监听。
- **原因**：bridge 继承的 stdout/stderr pipe 已无读取端；处理 HTTP 响应前 `log_message` 打印访问日志触发 `BrokenPipeError`，请求处理线程在写响应前退出。
- **处理**：正常重启 bridge，并将 stdout/stderr 重定向到 `/home/car/.ros/sim_bridge_11313.log`；小车轮询同时覆盖 `httplib.HTTPException` 并重连，120 秒未确认时继续主流程。
- **预防**：长驻 bridge 不得依赖临时终端 pipe；启动时将运行日志定向到持久文件，并用本机 `curl /status` 验证完整 JSON 响应。

### 2026-08-14：ROS 相机替换遗漏 FrameGrabber 的 `cam_fps` 运行时契约

- **现象**：终点交接已完成、ROS 图像已成功进入 lane_follow，首次输出性能行时却报 `RosFrameGrabber ... has no attribute 'cam_fps'` 并退出。
- **原因**：共享 ROS 相机新建 `RosFrameGrabber` 时只实现了最新帧缓存，遗漏原 V4L2 `FrameGrabber` 已被性能输出依赖的帧率字段与更新逻辑。
- **处理**：在 ROS 采集器中实现同等的 `cam_fps` 每秒统计；定向测试先复现属性缺失，再验证属性存在。
- **预防**：替换同一抽象的实现时，先检索所有调用方并以运行时属性契约写回归，不能只按最小取帧功能判断替换完成。
