# 2026-08-18

### 2026-08-18：OCR 分阶段停车误切 CymPlanner 车体模式导致降速

- **现象**：部署分阶段膨胀后，实车速度变慢；用户确认 CymPlanner 只有前视点模式正常，不能使用车体模式。
- **原因**：把“局部 inflation 分阶段切换”和“碰撞几何模式切换”错误绑定；`body_projection` 读取独立的低速参数，车端 `max_vel_x=0.07`，前视点模式为 `0.35`。
- **修复**：撤销 OCR 停车阶段的 `body_projection` 调用，改为只切换 local inflation，并显式保持 `point` 模式。
- **预防**：涉及碰撞安全的模式不能默认改变控制律；任何模式切换前必须对照车端实际参数，确认速度、增益和控制状态不发生未授权变化。

### 2026-08-18：旧 bridge 占用 11313 导致新仿真栈自清理

- **现象**：启动日志先出现 `GET /status 200`，随后新 bridge 报 `OSError: [Errno 98] Address already in use`；启动脚本清理 `task3_prepare.launch`，连带出现 Gazebo mutex 和 `ROSInterruptException`。
- **原因**：上一份 bridge 仍监听 11313；新 bridge 的 `/map` 就绪日志早于 HTTP socket bind，`SIMULATION_BRIDGE_READY` 不能证明新端口已成功监听。
- **修复**：停止旧仿真一键启动终端，确认 11313 只有一份 bridge，再重新启动并核对 `/status` 为 `state=waiting`。
- **预防**：每轮仿真只保留一份启动脚本；启动前后检查 bridge PID/11313 监听者，不能把 `SIMULATION_BRIDGE_READY` 单独当作 HTTP 服务就绪。

### 2026-08-18：bridge 就绪检查未绑定启动子进程

- **现象**：旧 bridge 已返回 `/status`，新 `sim_bridge.py` 随后因 `Address already in use` 退出，但启动器仍打印 bridge 已就绪并继续清理仿真。
- **原因**：启动器只按 `11313/status` 的内容判断就绪，没有确认监听端口实际归属于本次启动的 `BRIDGE_PID`；`SIMULATION_BRIDGE_READY` 又发生在 HTTP socket bind 之前。
- **修复**：启动前检查端口监听 PID；等待阶段同时验证子进程存活、端口归属和 `/status`，退出清理增加 SIGINT/SIGTERM/SIGKILL 有界升级。
- **预防**：任何多实例服务的 readiness 检查必须绑定进程身份或端口所有权，不能只验证共享 endpoint 的返回值。

### 2026-08-18：仿真 bridge 的 409 分支绕过 120 秒兜底

- **现象**：未启动 Gazebo 时，车端收到 `simulation already running` 后直接进入 `ABORTED`，没有等待 120 秒继续终点流程。
- **原因**：车端将 `/start` 的 HTTP 409 直接转换为 `MissionAbort`；120 秒只在后续 `/status` 轮询函数中计时。bridge 的 `running` 是内部单次运行状态，不等价于 Gazebo 已经正常运行。
- **修复**：409 改为告警并返回 `False`，沿用 `/status` 轮询；超时后继续车辆流程。相关改动记录为 `2026-08-18｜仿真 409 状态进入 120 秒兜底`。
- **预防**：任何仿真启动异常分支都必须验证是否能到达 `simulation_wait_done()`；单测同时覆盖 `/start` 返回 409 和调用方继续路径。

### 2026-08-18：仿真一键启动脚本只写入 Windows、未同步 WSL

- **现象**：Windows 工作区已有 `simulation/scripts/start_simulation_stack.sh`，但 WSL
  `~/smartcar2026/simulation` 执行入口时报 `No such file or directory`。
- **原因**：Windows 统一仓库与 WSL `/home/car/smartcar2026/simulation` 是两份工作副本；
  新增脚本未完成部署同步，且两份仓库的最新提交并不一致。
- **修复**：将脚本同步到 WSL 仿真目录的 `scripts/`，设置 `0755`，并用两端 SHA-256
  校验一致；随后在 WSL 按实际用户命令完成 `bash -n` 和 `--help` 验证。
- **预防**：新增或修改仿真启动入口后，必须同步到 WSL 实际运行副本，再做目标路径、权限、
  SHA-256 和最小命令回归；不能只验证 Windows 工作区文件存在。

### 2026-08-18：WSL Bash 命令混入 PowerShell 的 Select-Object

- **现象**：通过 `wsl.exe ... bash -lc` 读取 ROS 话题时，把 PowerShell 的 `Select-Object`
  写进 Bash 命令，Bash 报 `Select-Object: command not found` 并导致管道断开。
- **原因**：跨 Shell 调试命令未区分 PowerShell 与 Bash 的管道命令。
- **修复**：改用 Bash 原生 `head`，重新执行后完成 ROS Master、地图、TF 和激光检查。
- **预防**：传给 `bash -lc` 的字符串只使用 Bash 命令；需要截断输出时使用 `head`、`tail`，
  不把 `Select-Object`、`Where-Object` 等 PowerShell 命令嵌进去。

### 2026-08-18：PGM 文件白色像素实际为 254

- **现象**：生产地图像素修正脚本按白色值 255 校验时，在国赛墙位的空白像素处提前失败。
- **原因**：文件头最大值是 255，但现有 PGM 的空白像素实际统一为 254。
- **修复**：按文件现状将 PGM 空白值 254 纳入像素断言，保持文件头不变并只把目标像素置 0。
- **预防**：处理现有 PGM 前同时检查头部最大值和实际像素直方图，不能仅由 `maxval` 推断背景值。

### 2026-08-18：全局膨胀参数与 CymPlanner 局部判障范围不一致

- **现象**：车端全局代价地图已设置 `inflation_radius=0.22`，但 CymPlanner 的路径阻塞检查仍只读取 local costmap，修改全局膨胀参数没有直接触发局部重规划。
- **原因**：`CymPlanner::checkPathBlocked()` 接收的是 move_base 提供的 local costmap；global costmap 只参与 GlobalPlanner 的路径生成，未接入局部前视判定。
- **修复**：本轮将三个模式 `obstacle_cost_threshold` 统一设为 `1`，使当前 local costmap 的任意非零代价触发事件式重规划；未擅自扩大 local costmap 的膨胀半径。
- **预防**：调全局膨胀参数前先确认判定链路读取哪张 costmap；若要求全局膨胀带参与安全触发，必须同步 local 膨胀范围或显式接入 global costmap 数据。

### 2026-08-18：PowerShell 组装 SCP 目标路径混用 Windows 分隔符

- **现象**：批量同步 local costmap YAML 时，哈希命令拼出的远端路径丢失目录分隔符，校验失败。
- **原因**：PowerShell 本地路径使用反斜杠，直接用字符串替换构造 Linux SCP 路径，未显式维护远端 POSIX 目标路径。
- **修复**：先只读确认车端目标文件，再为每个文件显式指定 Linux 目标路径，重新上传并完成三份 SHA-256 校验。
- **预防**：Windows→Linux SCP 批量部署使用显式本地/远端路径映射，不用跨平台字符串替换生成远端路径。

### 2026-08-18：误把“延迟开启局部代价地图”实现成关闭整个 local_costmap

- **现象**：如果直接关闭 `/move_base/local_costmap`，点 3 之前 CymPlanner 的 `isCurrent()` 检查会失败，导航无法正常输出速度。
- **原因**：用户要延迟的是实时动态障碍判障/膨胀，不是让 local costmap 容器和静态地图完全消失；CymPlanner 仍依赖 local costmap 的 current 状态。
- **修复**：只通过 dynamic_reconfigure 关闭 `obstacle_layer` 和 `inflation_layer`，保留 local costmap、StaticLayer 和 current 更新；点 3 导航成功返回后再同时打开两层。
- **预防**：涉及 costmap 生命周期时，先区分容器、StaticLayer、ObstacleLayer、InflationLayer；修改后必须检查 planner 的 `isCurrent()` 前置条件和点 3 前后的日志时序。

### 2026-08-18：相机设备固定使用 `/dev/video0` 导致 QR 阶段启动失败

- **现象**：车辆到达点 52 后，调用 `/usb_cam/start_capture` 返回 V4L2 `unable to configure stream (19)`，任务在 QR 阶段 ABORTED。
- **原因**：车端只存在 `/dev/video1`，`/dev/video0` 不存在；`v4l2-ctl` 同样报告无法打开 `/dev/video0`，USB Camera 实际枚举在 `/dev/video1`。USB 重新枚举后，固定设备编号失效。
- **预防**：相机 launch 和任务参数不得依赖可变的 `/dev/videoN`；应使用 `/dev/v4l/by-id/` 稳定路径，并在任务启动前只读检查目标设备存在、可打开且没有被占用。

### 2026-08-18：USB 热重连后 usb_cam 保留失效文件描述符

- **现象**：改用 `/dev/ucar_camera` 后，车辆仍在点 52 的 `/usb_cam/start_capture` 处收到 `Video4linux: unable to configure stream (19)`。
- **原因**：04:19:04 USB Hub、摄像头和音频设备整体断开，04:19:05 摄像头重新枚举；`usb_cam` 进程没有重新打开设备，点 52 时用旧 fd 执行 `VIDIOC_QBUF`，返回 `ENODEV(19)`。稳定 udev 别名只解决“下一次 open 找哪个节点”，不能修复进程内已经失效的 fd。
- **对比**：当前 `/dev/ucar_camera` 已跟随到 `/dev/video1`；设备列出 YUYV 640×480 和 MJPG，车端用两种格式直接采 3 帧均成功，因此不是路径或像素格式问题。
- **预防**：相机节点必须在 `ENODEV`/USB 热重连后重新 open、重新设置格式、重新申请 mmap buffer；或者在 QR 启动前确认相机节点已随设备重连而重启。稳定别名仍保留，用于重新 open 时避免依赖 `/dev/videoN`。

### 2026-08-18：QR 分类器超时后响应串给下一个二维码，导致扫描阶段反复

- **现象**：`耳机` 识别后任务等待约 60 秒并报 `no reply from classifier helper`；随后 `毛巾` 在 16ms 内被记录为 `电子产品`，`蛋糕` 在 12ms 内被记录为 `日用品`，目标收集停在 `1/2` 并继续重复扫描。
- **原因**：任务对分类器只按时间等待单行响应；当前 `spark_timeout=60s`，前一个请求超时后 helper 仍可能在后台重试，管道没有请求 ID、取消或响应丢弃机制，后续二维码读取了前一个请求的迟到响应。
- **证据**：独立调用同一车端 helper 对 `毛巾` 返回 `日用品`、对 `蛋糕` 返回 `食品`；车端相机/QR 日志仍持续产生 `PRODUCTION_QR_EVENT` 和 `PRODUCTION_QR_API_EVENT`，导航目标也均 `GOAL_REACHED`。
- **修复**：三套主流程与 helper 增加 `request_id` 配对、超时销毁旧 helper、8 秒单次分类上限和分类失败重试；同一二维码的分类结果取最新记录。关联改动记录：`ucar_source_code/docs/changes/2026-08-18-fix-qr-classifier-response-desync.md`。
- **预防**：分类请求必须具备请求 ID/顺序校验和超时取消；在修复前不要启用会阻塞主流程的远程分类，至少要让本地关键词分类在远程超时后立即返回，且不能把迟到响应交给下一项。

### 2026-08-18：OCR 内墙停车偏移未与现场要求保持一致

- **现象**：OCR 停车参数曾由默认的 `0.25m` 显式覆盖为 `0.29m`，与现场确认的墙内 25cm 停靠要求不一致。
- **原因**：把一次针对停车误差的参数试调固化到三套 launch 和几何测试，未保留比赛要求的 25cm 作为当前配置。
- **修复**：三套 launch、几何测试和运维核对统一恢复 `ocr_stop_offset_m=0.25`；历史变更文档保留为历史记录。
- **预防**：涉及比赛几何约束的参数调整必须同时记录现场验收基准，并在 launch、测试和运维文档中统一核对；未经现场确认不得把试调值设为当前默认。
