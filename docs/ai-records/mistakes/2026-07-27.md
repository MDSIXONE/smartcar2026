# 2026-07-27

### 2026-07-27：WSL 隔离构建的网络初始化与跨 Shell 引号处理失败

- **现象**：首次验证假定 `/home/car/.config/smartcar/ros_network.sh` 存在，但当前 WSL 中没有该文件；随后把动态 IP 提取逻辑嵌入 PowerShell、WSL 和 Bash 的多层命令时，又先后出现 `awk` 解析错误、`cut` 参数被错误拆分以及命令提前退出。通过 `env` 传入的变量还会被 `bash -lc` 的登录初始化清空。
- **原因**：没有先检查共享网络配置文件是否存在，并在一条跨 Shell 命令里同时完成地址发现、字符串解析和构建，导致不同 Shell 的变量展开、登录初始化和引号规则互相干扰。
- **修复**：先用独立的只读 WSL 命令获取当前地址；构建与测试在明确的临时目录内完成；需要 ROS 网络的命令则在加载 ROS 环境后，把已获取的地址直接写入当前 Bash 命令并导出 `ROS_IP` 与 `ROS_MASTER_URI`。
- **预防**：执行 WSL 验证前先检查网络配置文件；把动态地址发现与实际构建拆成两个步骤；网络变量必须在最后一次 `source` 之后设置；跨 PowerShell/WSL/Bash 调用时避免嵌套文本解析、仅依赖继承环境变量和脆弱的多层引号。

### 用周期性 set_model_configuration 保持机械臂姿态导致行进中夹爪抖动


- **现象**：小车导航行进过程中机械爪持续抖动、机械臂模型乱飞；静止时完全正常。
- **原因**：`task3_prepare.launch` 传入 `hold_initial_arm_pose=true`，
  `set_arm_initial_pose.py` 因此以 30 Hz 调用 `/gazebo/set_model_configuration`。
  该服务内部会「暂停世界 → `SetJointPositions` 瞬移所有关节 → 恢复世界」，
  行进中每秒 30 次清空关节速度与接触状态，求解器每帧从与底盘动量矛盾的初值
  重启，关节数值发散；同时 `r_joint` 走 `gazebo_ros_control` 的
  `PositionJointInterface`（仓库未配置 `pid_gains`），即使 `gripper_controller`
  处于 stopped，`writeSim()` 仍每步把它拉向初始化命令 `0.0`，与 hold 写入的
  `1.0` 正面冲突，再由五个 mimic 插件逐帧放大到指节。碰撞或急停一叠加，
  `arm_joint5` 峰峰值达 3.03 rad、`r_joint` 达 1.90 rad 并越过 ±1.51 限位。
- **修复**：`task3_prepare.launch` 改为 `hold_initial_arm_pose=false`。
  同一 launch 的 `disable_arm_gravity=true` 已足够保持停放姿态；带加减速的
  前进/旋转/后退剖面实测 26 秒，每秒关节峰峰值不超过 0.008 rad，
  首尾漂移不超过 0.0002 rad。
- **预防**：控制器停用期间不得用 `/gazebo/set_model_configuration` 之类
  会暂停世界并重置物理状态的接口做周期性保持；只能用重力/阻尼等纯物理手段。
  新增此类「周期性写 Gazebo 状态」的逻辑前，必须先做运动状态下的关节峰峰值
  对照实测。

  仿真就连续复测，小车已停在障碍上，第二次测量整体无效。
- **修复**：改用带加减速的前进、原地旋转、后退组合剖面，并在报告中同时输出
  `base_footprint` 的 x 位移与逐秒峰峰值，确认底盘真在运动后才比较结论。
- **预防**：任何运动学对照实测都必须每次重启仿真，并先验证底盘实际位移，

### 固定关节建立后回写滞后的实际夹爪角导致立即释放


- **现象**：运行探针中固定关节服务报告成功连接物块，但约 `30 ms` 后又立即
  调用拆卸与动态物块恢复，表现为吸附仍然无法保持。
- **原因**：夹爪收到 `0.76` 闭合命令后，物理关节尚未收拢，实际反馈仍接近
  `1.0`。固定关节建立成功时，`grasp_attach.py` 又把这个滞后的实际角度发布到
  `/gripper_controller/command`；同一节点的命令回调把大于 `0.89` 的值视为明确
  开爪意图，从而自触发释放。
- **修复**：固定关节建立后不再回写实际关节角，保持调用方原始闭合命令；
  回归测试用“命令已闭合、反馈仍为开爪”的状态确认不会产生新的夹爪命令。
- **预防**：控制意图只能来自任务命令，不能用可能滞后的执行器反馈反向覆盖；
  所有吸附/释放状态机必须在实际 Gazebo 中核对服务时序，不能只依赖模拟单元测试。

- **预防**：部署守卫的进程匹配必须先验证返回的 PID 与命令行，不能只根据
  `pgrep` 的退出码判定仿真残留。

### 恢复官方 world 后仍按墙钟等待机械臂轨迹


- **现象**：官方 `grasp_attach.py` 在实时 TCP 放置实验中能自动吸附，距离
  稳定在 `3.4–6.4 mm`；但完整任务两次都在物理夹取和官方兜底阶段失败，
  报告 TCP 框内没有物块。
- **原因**：官方 world 的 `max_step_size=0.001` 在当前机器上实时率约为
  `0.25`，而 `_move_arm()` 用墙钟等待轨迹的仿真时长。标称 2 秒的轨迹只运行
  约 0.5 秒仿真时间，任务便提前闭爪、抬升和执行兜底，TCP 实际尚未到位。
- **修复**：新增基于 `/clock` 的 `_wait_for_sim_duration()`；普通机械臂轨迹、
  带腕部碰撞保护的下探轨迹和保护后的回退轨迹都等待足够的仿真时间。
- **预防**：Gazebo 中 `JointTrajectoryPoint.time_from_start` 属于仿真时间；
  任何后续动作都必须以 `/clock` 或到位反馈为前置条件，不能假设 RTF 为 1
  后直接用墙钟 `sleep`。

### 把三个独立观察导航点误当成顺时针原地搜索


- **现象**：任务配置和日志显示按“左、中、右”访问，但实际没有遵守“左侧
  找不到 → 顺时针旋转 90°找上方 → 再顺时针旋转 90°找右侧”的规则。
- **原因**：三个 `observation_goal` 的 yaw 虽然恰好依次减少约 `π/2`，XY
  却各不相同；状态机只校验列表顺序，没有约束同一观察点、旋转方向和角度，
  因而执行的是三次独立导航。历史分支也沿用了这个缺陷。
- **修复**：将区域语义统一为 `left/upper/right`，三个目标共用左侧观察点
  XY，yaw 严格按 `π → π/2 → 0`；参数解析新增不变量检查，任何平移或非
  顺时针 90°步进都会拒绝启动，并增加无检测/非目标两条状态机回归。
- **预防**：扫描顺序不能只靠配置名称和近似数值表达；涉及方向、角度、原地
  约束的行为规则必须在参数入口验证，并在真实状态机调用层覆盖各失败分支。

### 把旋转搜索修复成唯一搜索路径，遗漏旧观察位兜底


- **现象**：第一版规则修复把三个观察目标全部改为同一 XY 的顺时针旋转，
  若旋转视角因遮挡或框偏移均未确认目标，只能重新开始同一轮扫描。
- **原因**：把“遵守旋转寻找规则”理解成替换旧版观察点，而用户需要的是优先
  旋转搜索、全部失败后再用原有三组 XY+yaw 依次复查。
- **修复**：保留 `observation_goal` 作为同 XY 的旋转主路径，新增
  `fallback_observation_goal` 保存原有左/中/右三组位姿；一次搜索周期先执行
  主路径，再执行旧版兜底，并在终端逐步输出到位、识别、非目标、旋转和切换阶段。
- **预防**：新增搜索策略时必须明确它与旧策略是替换、并行还是分层兜底；
  可靠性路径的旧覆盖范围不得在未确认的情况下直接删除。

### 重构搜索辅助函数后源码范围测试仍截取旧入口


- **现象**：WSL 单元测试首次运行时 18 项通过、1 项失败；失败项报告找不到
  `observation_pose=True`，但状态机行为测试与实际代码均已把该参数传入。
- **原因**：测试通过字符串切片检查 `_find_and_align_target_once()` 的源码，
  重构后参数已移入它调用的 `_search_target_at_observation()`，旧切片不再覆盖
  真正实现。
- **修复**：把检查范围起点调整到新的搜索辅助函数，并重新执行相关 19 项
  单元测试、完整 CTest 和 ROS 测试，结果全部通过。
- **预防**：重构后同步复核依赖源码文本范围的测试；优先用行为断言覆盖跨函数
  语义，必须检查源码时应从最小实际实现入口截取到稳定的下一边界。

### 恢复官方 world 绝对 URI 后场区文字消失


- **现象**：食品、日用品和电子加工区的边框仍在，但墙面场区文字不显示。
- **原因**：为保证 `math.world` 与官方资源包一致，把挂牌 URI 恢复成了官方
  写死的 `/home/ucar/gazebo_ws/...`；实际部署位于
  `/home/car/smartcar2026-simulation`，而原回归只校验 URI 字面值和仓库内
  OBJ 存在，没有验证部署机能否解析该绝对路径。
- **修复**：不修改 `math.world` 或 URDF；新增启动兼容节点，仅在官方绝对
  路径不存在时，通过 `model://` 加载仓库内同一份官方 OBJ 作为无碰撞可视
  覆盖层。GUI 实拍确认文字恢复，日志确认三块挂牌均成功加载。
- **预防**：资源基线测试要同时区分“源文件与官方一致”和“部署环境可解析”；
  对官方写死路径采用启动时兼容层，不能只锁定 XML 字面值便判定渲染可用。

### 并发收臂改动后旧夹取测试夹具未模拟新入口


- **现象**：新增并发测试通过后，既有夹取顺序测试有两项因缺少
  `arm_joint_state_lock` 报错，而不是产生业务断言失败。
- **原因**：吸附路径从阻塞 `_move_arm()` 改为直接调用
  `_publish_arm_target()`，旧测试夹具只替换了前者，导致测试意外进入真实关节
  状态读取逻辑。
- **修复**：在旧夹具中同时模拟非阻塞轨迹发布，并把官方吸附路径的期望更新为
  “下探阻塞、收臂非阻塞”；保留纯物理路径原有阻塞行为。
- **预防**：改变状态机调用入口时，先搜索所有替身和夹具；回归既要断言动作
  顺序，也要明确区分阻塞与非阻塞接口，避免测试因未初始化对象内部状态而误报。

### 重复比较解压副本，误阻塞已确认官方基线的发布


- **现象**：当前仓库的 URDF/world 已由负责人确认为官方基线，但验收又拿另一
  个解压副本做哈希和文本差异比较，并据此把主分支发布标记为阻塞。
- **原因**：没有区分“负责人确认的正式仓库基线”和“用于追溯的外部副本”，
  把跨副本比较擅自提升成新的发布门槛。
- **修复**：按负责人结论取消外部副本差异判定；正式验收只用仓库内哈希防止
  URDF/world 后续被意外修改，并恢复主分支发布。
- **预防**：资源权威来源由项目负责人和正式仓库共同确定。已明确基线后，测试
  应检查其未发生变化，不能自行引入另一个副本覆盖发布决策。

### 正式启动默认关闭 Gazebo GUI，遗漏比赛可见性要求


- **现象**：`task3_prepare.launch` 的 `gui` 默认值为 `false`，按默认命令启动
  时只有后台 Gazebo，不能满足比赛期间 Gazebo 与 RViz 同时可见的硬性要求。
- **原因**：此前主要关注自动任务和性能，未把官方可见性要求落实为启动默认值
  和回归断言。
- **修复**：先增加失败测试，再把正式启动入口的 `gui` 默认值改为 `true`；
  WSL 使用不带覆盖参数的默认命令实测确认 `gzclient` 和 RViz 同时启动。
- **预防**：官方要求中的可见 UI、话题和算法限制均应落成机器可检查的默认值
  或测试，不能只写在操作说明里。

### 手工指定 unittest 方法名与实际测试名不一致


- **现象**：定向执行单个测试时出现 `AttributeError`，提示指定的方法不存在，
  实际尚未运行目标断言。
- **原因**：根据语义手写了一个近似方法名，没有先从测试文件或测试列表复制
  准确名称。
- **修复**：查询真实方法名后重新执行，得到预期红灯，再完成修改并执行完整
  测试集。
- **预防**：定向运行测试前使用 `rg` 或测试收集结果确认完整节点名；测试运行
  器报错与断言失败必须分开判断。

### WSL 非交互构建遗漏 ROS 环境


- **现象**：WSL 仓库已成功快进到新提交，但紧接着执行 `catkin_make` 报
  `command not found`。
- **原因**：本次使用 `bash -lc` 的非交互 shell，没有先加载
  `/opt/ros/noetic/setup.bash`，不能假设用户交互终端的环境会自动继承。
- **修复**：在同一非 root 用户 `car` 下显式加载 ROS Noetic 环境后重新构建，
  编译成功。
- **预防**：所有自动化或跨 Windows/WSL 的非交互 ROS 命令都应在命令内明确
  `source /opt/ros/noetic/setup.bash`；文档中的少量启动命令仍可通过用户 shell
  配置减少重复输入，但验收脚本不能依赖该隐式状态。

### WSL 单分支克隆未登记 main 的 fetch refspec


- **现象**：已取得 `origin/main` 提交后执行
  `git switch -c main --track origin/main`，Git 仍提示起点不是可跟踪分支。
- **原因**：WSL 仓库最初按单分支部署，`remote.origin.fetch` 只登记了历史
  功能分支；手工写入远端跟踪引用不会自动扩展该配置。
- **修复**：为 `origin` 增加标准的
  `+refs/heads/main:refs/remotes/origin/main` refspec，再创建并跟踪本地
  `main`，源码和未跟踪资产均未改动。
- **预防**：把单分支部署切换为正式主分支前，同时检查引用是否存在以及
  `remote.origin.fetch` 是否覆盖目标分支，不能只检查 `rev-parse`。

### 在 PowerShell 中把通配符路径直接传给 rg


- **现象**：使用 `rg ... src/car3/launch/*.launch` 时返回“文件名、目录名或
  卷标语法不正确”，没有完成 launch 引用检查。
- **原因**：PowerShell 没有按预期替 `rg` 展开该通配符，Windows 路径 API
  收到了带 `*` 的字面文件名。
- **修复**：改为把目录传给 `rg`，并使用 `-g '*.launch'` 过滤；随后重新完成
  正式启动链和冗余文件引用审计。
- **预防**：Windows 下使用 `rg` 时优先采用“目录 + `-g`”模式，不把 shell
  通配符拼进路径参数。

### 大批量补丁依赖了不完整的上下文


- **现象**：第一次同时修改多个文件并删除冗余资源时，补丁因
  `gazebo_nav.launch` 中间还存在一行注释而整体校验失败。
- **原因**：构造补丁前只查看了检索摘要，没有读取目标位置的完整相邻上下文。
- **修复**：确认所有文件均未被部分修改后，把变更拆成小补丁，并逐个使用准确
  上下文完成；二进制训练数据则在验证绝对路径后用 Git 删除。
- **预防**：跨多个文件的补丁先读取每个修改点的实际上下文；大量删除与逻辑
  修改分开执行，保证失败时容易确认原子性和恢复范围。

### 旧工作树清理混用了批量递归删除与只读 Git 对象


- **现象**：把四个已核验目录放入一个 PowerShell 循环递归删除时被安全策略
  拒绝；随后尝试把旧主工作树送入回收站也因权限失败，直接删除又被 `.git`
  内的只读对象中断。
- **原因**：没有优先使用 Git 自身的工作树移除机制，也没有预先考虑 Windows
  Git 对象可能带只读属性；一次脚本承载多个递归删除目标也不利于安全审计。
- **修复**：先保留并验证独立的最终仓库，再用 `git worktree remove --force`
  逐个移除关联工作树；对剩余旧主仓库和官方解压副本逐项核验绝对路径、解除
  文件只读属性后删除，最后才把独立仓库移动到正式目录。
- **预防**：清理多工作树仓库时先查 `.git` 指向和 `git worktree list`；
  每个递归目标单独核验、单独执行。主工作树需删除时先建立并验证独立克隆，
  并在 Windows 上预先处理只读文件，不能直接批量 `Remove-Item`。
