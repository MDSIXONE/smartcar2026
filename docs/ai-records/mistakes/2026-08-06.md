# 2026-08-06

### 2026-08-06：PD 对齐速度低于底盘 MCU 旋转死区，车"转不动"导致对齐超时

- **现象**：生产任务点 25 OCR 对齐 ABORT：`protected alignment did not reach 0.022 rad of
  measured yaw within 2.5 s (actual=0.004 required=0.012)`——PD 输出 0.073 rad/s 发布
  2.5s，odom 实测只转 0.004 rad，车几乎没动；而 QR 阶段 0.18 rad/s 能正常转动。
- **原因**：底盘 MCU 固件有旋转死区，极小角速度指令（经轮速公式换算成极小 PWM）被电机
  死区吞掉；死区阈值实测在 0.073~0.18 rad/s 之间。base_driver.cpp 的
  `angular_speed_min_=0` 未参与钳制，任务 Python 的 alignment_angular_speed（纯 PD）
  也无最小速度输出——没有一层兜住小速度。
- **修复**：`rotate_in_place_for_yaw` 发布速度前钳制到死区之上：新增参数
  `ocr_alignment_min_speed`（默认 0.12 rad/s），`abs(speed) < min_speed` 时改为
  `min_speed * direction`；超转由 progress 每帧累计（positive_turn_increment）与
  到达后 stop + wait_for_chassis_stop 约束，超出部分由下一轮 PD 反向修正。
- **预防**：涉及底盘小速度/小位移指令一律先确认高于实车死区；死区随电压/负载漂移，
  更换电池或载荷后需复查该阈值。

### 2026-08-06：Py2 rospy.loginfo 中文参数与 JSON 中文 bytes 导致任务崩溃

- **现象**：实车 mission 在 QR 阶段多次 ABORT：`unexpected task error: 'ascii' codec can't
  decode byte 0xe6/0xe9 in position 80`。第一次是 `classify_qr_text` 把 UTF-8 bytes
  （中文二维码文本）直接交给 `json.dumps`（Py2 对 str 隐式 ASCII 解码）崩溃；第二次是
  helper 返回的中文 category（unicode）被 `encode("utf-8")` 成 bytes 传给
  `rospy.loginfo("%s", ...)`，rospy 序列化时再次 UnicodeDecodeError。任务状态名
  `PRODUCTION_OCR_TURN_025_日用品` 中的中文也来自此路径。
- **原因**：Python 2 中 `str` 是 bytes、`unicode` 是文本；`json.dumps` 与
  `rospy.loginfo/logerr` 的 `%` 拼接都会对非 ASCII bytes 隐式解码，任何一步含 UTF-8
  中文都可能在 ROS XML-RPC/日志序列化处崩溃；任务主循环任何未捕获异常都直接 ABORT。
- **修复**：新增 `log_safe_text(value)`：bytes → `decode("utf-8","replace")` 成 unicode，
  再 `json.dumps(value, ensure_ascii=True)` 转成纯 ASCII 转义（`\u98df\u54c1`）；任务侧
  全部 loginfo/logerr 的中文参数与含中文的 msg 本身一律改 ASCII/转义；`classify_qr_text`
  入口先 `decode("utf-8","replace")` 归一化 QR 文本（Py2/Py3 双兼容）；`json.dumps`
  payload 只接收 unicode。helper 端 `emit` 保持 `ensure_ascii=True`。
- **预防**：Python 2 任务代码禁止在日志/JSON 直接使用非 ASCII；跨进程文本协议统一
  unicode + `ensure_ascii`；新增日志先自查 msg 与参数均为 ASCII；实车验证回归以
  `PRODUCTION_SPARK_CLASSIFY` 日志出现 `\u` 转义为准。

### 2026-08-06：base_driver 启动期 odom/imu 瞬断永久锁死安全门

- **现象**：任务启动初期 base_driver 偶发两次 `BASE_odom_PUBLISH_GAP 1.03s` +
  `BASE_imu_PUBLISH_GAP 1.03s`（两流同时断 1.03s 后自行恢复 20Hz），任务节点从此持续
  `waiting for safety gate: Odom sensor not active any more` 直到 45s 超时 ABORT。
- **原因**：rosout_cb 把 "odom sensor not active"/"imu sensor not active" 写入
  `critical_error` 后从不清除；安全门检查的是**当前** odom 健康（≥10 连续有限帧 +
  TF 新鲜 ≤0.5s），启动期一次性瞬断不应永久锁死。
- **修复**：新增 `clear_sensor_alive_error()`：odom_cb 连续有限帧 ≥10 时，仅清除
  "odom sensor not active"/"imu sensor not active" 类错误；crc16/head_len/tf_nan_input/
  non-finite 结构性错误保持永久（需重启链路）。
- **预防**：传感器"不活跃"类告警应按当前健康状态复位，结构性错误才永久锁死；实车低压
  持续断流时错误会再次置位，安全门依然不过，原防护不受影响。

### 2026-08-06：Windows 管道中文乱码导致本地验证误判

- **现象**：开发星火 QR 分类 helper 时，在本机 PowerShell 用管道把含中文的 JSON 喂给
  Python 3 helper，本地关键字匹配全部失败（`旺仔牛奶`、`手机充电器` 都返回 `none`）；
  改用 UTF-8 文件重定向后全部正确。另发现 helper 若在小车端以 Python 2 运行且
  `LANG=C`，stdin 默认按 ASCII 解码中文会直接崩溃。
- **原因**：Windows 默认 locale（GBK）下，PowerShell → Python 的 stdin 字节流中文乱码；
  第一次误以为是匹配逻辑错误，实际是输入编码问题。小车端 Python 2 的 stdin 解码依赖
  locale，不能假设 UTF-8。
- **修复**：helper 启动时强制 stdin/stdout 为 UTF-8（Python 3 用 `reconfigure`，
  Python 2 用 `codecs.getreader/getwriter`）；本机验证改用 UTF-8 文件作为输入。
- **预防**：跨进程文本协议一律显式 UTF-8 并两端固定；Windows 下本地验证 Python 中文
  输入时不要依赖管道默认编码；任务侧 Python 2 打印中文 unicode 前先转 UTF-8 字节
  （`isinstance(s, str)` 判 False 后 `encode("utf-8")`），`json.dumps` 保持
  `ensure_ascii` 转义输出。
