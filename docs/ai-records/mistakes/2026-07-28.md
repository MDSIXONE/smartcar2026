### 2026-07-28：车端部署校验路径、远程引号、权限与 Catkin 白名单错误

- **现象**：首次 SHA-256 校验在远程执行 `cd ~/ucar_ws` 后仍使用 `ucar_ws/src/...`，导致 27 个已上传文件全部误报不存在；随后 PowerShell 抢先解释了发往远程 Bash 的 `$(ip ...)`，构建在 `catkin_make` 前退出；修正引号后，`libcym_planner.so` 已编译，但车端缓存白名单未包含新包 `ucar_2026`，`--pkg ucar_2026` 因没有构建目录而失败；Windows `scp` 后两个脚本也未保留预期可执行位。

- **修复**：校验改为从小车家目录执行，并确认 27 个文件哈希全部匹配；远程命令改用单引号包裹的 Bash 脚本和本次已确认的显式网络地址；白名单保留 `cym_planner`、`jie_ware`、`yolo2025` 并加入 `ucar_2026` 后重新构建；两个车端脚本显式设为 `0755`；最终构建及 14 项测试全部通过。收尾时还恢复了 WSL 的当前 `192.168.8.199/24` 地址，并停止一个仅绑定回环地址、没有业务节点的旧 Master。
- **预防**：校验路径以 `ucar_ws/` 开头时固定从 `~` 执行；将网络发现和远程构建拆成独立步骤；跨 PowerShell/SSH/Bash 时不嵌套本地可解释的命令替换；构建前先核对 Catkin 白名单；Windows 上传脚本后执行 `stat` 并显式设置 `0755`；结束前检查 WSL 与小车的 ROS 进程、监听地址和实际业务节点。

### 2026-07-28：Windows CRLF 破坏车端 Python shebang

- **现象**：首次真机启动时 `navigation_scan_relay` 持续以退出码 127 重启，日志为 `/usr/bin/env: ‘python2\r’: No such file or directory`；由于 `/scan_raw -> /scan` 中继未启动，`lidar_loc` 无法建立 `map` TF，`move_base` 一直等待 `base_link -> map`。
- **原因**：Git 索引中的脚本为 LF，但仓库没有 `.gitattributes`；Windows 工作树在检出时转换为 CRLF，`scp` 又逐字节复制到 Ubuntu 18.04，使 shebang 以 `0d 0a` 结束。Python 2 存在，脚本文本和解释器路径本身均正确。
- **修复**：立即发布零速度并停止失败的车端 launch；新增 `.gitattributes` 强制 `*.py`、`*.sh` 使用 LF，规范化 `navigation_scan_relay.py` 与 `stop_2026_task.sh` 后重新上传并设为 `0755`。车端首行确认仅以 `0a` 结束，完整重启后 relay、定位、`move_base` 与本地 RViz 均正常连接。
- **预防**：从 Windows 部署脚本前检查 `git ls-files --eol` 必须显示 `w/lf`；上传后用 `od -An -tx1` 检查 shebang 不含 `0d`；真实启动测试必须等待 relay ready，再执行有限里程计、两条 TF 和扫描频率安全门检查。

### 2026-07-28：跨机 roslaunch 的 XML-RPC multicall 响应卡在 WSL 发送队列

- **现象**：小车两次执行无自动目标 `2026.launch`，都在 `load_parameters starting ...` 停住；Master 中只有 `/rosout`，没有底盘、激光或 move_base 节点。中断堆栈显示 Python 2 `xmlrpclib` 正在等待 `system.multicall` 的 HTTP 状态行。
- **原因**：最小化后，车端空 `system.multicall([])` 在 HTTP/1.1 下 10 次有 7 次超时，而同一请求在 WSL 本机 10/10 成功、HTTP/1.0 下 20/20 成功。ROS 会在服务端 Linux 内核早于 4.16 时自动禁用 HTTP/1.1；但 Master 位于新内核 WSL，无法感知远端小车仍为 4.9 内核，因此启用了会在当前 WSL 镜像网络路径中间歇卡住的 HTTP/1.1。WSL 端对应 TCP 连接的 275 字节响应会保持未确认，小车一直收不到 HTTP 状态行。
- **修复**：新增只对 WSL ROS Master 进程树生效的 `sitecustomize.py`，在明确的环境变量保护下把 ROS XML-RPC 请求处理器固定为 HTTP/1.0；`start_ros_master.sh` 启动前验证协议确为 HTTP/1.0，兼容文件缺失时拒绝启动。没有修改 `/opt/ros`、Windows 网卡卸载、防火墙或小车系统配置。
- **预防**：Master 启动行必须包含 `XML-RPC=HTTP/1.0`；静态启动前用车端空 multicall 连跑 20 次作为零运动回归。完整启动验收仍先观察 Master 是否出现 `/move_base`；若日志停在 `load_parameters`，同时检查两端 `ss -tpn` 和 roslaunch 堆栈，不得发送目标。

- **预防**：读取 `/proc/<pid>` 前必须在同一远程 shell 中重新解析并验证 PID，或直接按当前 ROS 网络配置查询；不得跨命令缓存短生命周期进程号。

### 2026-07-28：误用 rosrun --help 启动了任务节点

- **现象**：为了确认 Catkin 入口，执行 `rosrun ucar_2026 production_task_2026.py --help`；ROS Python 节点没有普通 CLI 帮助语义，进程实际启动并等待 move_base，而不是打印帮助后退出。
- **原因**：把 ROS 节点入口当作常规命令行程序验证，没有使用只读的 `roslaunch --nodes`、`rospack find` 或文件链接检查。
- **修复**：按精确 PID 先发 SIGINT、再发 TERM，确认命令退出；车端当时没有 move_base 或导航 launch，节点只在等待 action server，未发送目标。随后额外发布有界零速度并检查无残留。
- **预防**：禁止用 `rosrun <node> --help` 验证 ROS 节点可执行性；静态检查使用 `python2 -m py_compile`、`roslaunch --nodes`、`rospack find` 和文件哈希，任何会调用 `rospy.init_node` 的入口均按真实启动处理。

### 2026-07-28：OCR 接口假设、远程超时与 launch 上传目录连续出错

- **现象**：未先确认车端既有 OCR 接口就按 Tesseract 设计并启动 `apt-get update`；本地 SSH 工具超时后，远端 apt 子进程仍继续运行。随后车端构建命令再次把远端 `awk` 放进 PowerShell 字符串，命令在本地解析失败。部署时又把 `launch/2026.launch` 与包根文件放在同一个多源 `scp` 中，导致它以 basename 误传为 `~/ucar_ws/src/ucar_2026/2026.launch`，与正式 `launch/2026.launch` 重名，`roslaunch` 静态解析拒绝继续。
