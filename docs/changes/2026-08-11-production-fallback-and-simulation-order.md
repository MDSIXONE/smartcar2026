# 2026-08-11 生产任务补充巡航与仿真顺序

## 目的

按现场流程修正 2026 双物品生产任务：二维码收齐后必须在前往点 3 前播报；实物放入与播报必须先于仿真物品停泊和仿真启动；找不到类别时不再中止整条任务，而是完成指定补充巡航后转点 441 交接；仿真完成等待限制为 150 秒。

## 涉及文件

- `ucar_ws/src/ucar_2026/scripts/production_task_2026.py`
- `ucar_ws/src/ucar_2026/scripts/production_task_geometry.py`
- `ucar_ws/src/ucar_2026/launch/2026.launch`
- `ucar_ws/src/ucar_2026/test/test_production_task_geometry.py`

## 行为

1. QR 阶段收齐两件实际物品、完成分类后，先同步播报“二维码识别完成，已获取<实物>和<仿真物品>”以及两件物品的仓库归属，再导航到点 3。
2. 内侧主巡航仍为 `12,22,13,23,...,19,29`。每个到达点的 360° OCR 可同时记录现实与仿真类别；即使先识别到仿真类别，也只保存墙面位置，继续寻找现实类别。
3. 找到现实类别后，车辆先到现实墙面停泊并完成“已将<实际二维码物品名>放入<类别>”的同步播报。之后才允许驶向已记录的仿真墙面，或继续寻找仿真类别，再发送仿真 `/start` 请求。
4. 主路线未找到仍需要的类别时，补跑：`1–10 → 20 → 30 → 40 → 39–31 → 21 → 11`。补充路线每点也执行 360° OCR。其边界格没有可用的中线四点守卫映射，因此保留任务安全门和 `move_base` 动态障碍层，不伪造静态守卫顶点。
5. 两条路线都完成后仍缺少任一需要类别，停止 OCR、释放相机、直接导航到 441，并发布 `SUCCEEDED` 以交接循迹任务；结果原因会明确记录未定位的类别，且不会启动仿真。
6. `simulation_done_timeout` 默认值及 launch 参数均为 `150` 秒；仿真失败或超过此限制仍按既有安全策略中止。
7. 目标守卫审计事件现带有路线名称和当前路线的下一目标，补充路线不会再错误引用主路线的下一站。

## 验证

- 本机 Python 语法检查通过：`production_task_geometry.py`、`production_task_2026.py`。
- `python ucar_ws/src/ucar_2026/test/test_production_task_geometry.py`：81 tests OK，66 个 ROS 依赖用例按既有条件跳过。
- 纯几何检查确认主路线的 16 个点仍可建立 64 个四点守卫；补充路线边界点不再送入该仅适用于内侧格的加载器。
- 已新增回归断言：二维码播报发生在点 3 前；仿真位置先被记录时，现实物品播报仍先于仿真停泊；补充路线未找到仿真类别时继续目的地而非抛出 `MissionAbort`。

## 已知限制

- 本机没有车端 ROS Melodic 依赖，包含真实 `rospy` 任务状态机的 66 项用例未在本机执行；部署前仍需在车端运行该包的 Python 2 / Catkin 回归。
- 补充路线边界格依赖导航代价地图与通用安全门进行动态避障，不具备主路线内侧格的“目标四顶点”精确跳过策略。

## 模型路由与复核

- **分析/复核**：GPT-5.6 Sol High，关注路线状态机、停泊顺序和安全守卫适用范围。
- **执行**：明确的 Python/launch/测试补丁；未改变底盘安全门、主路线守卫、仿真失败处理或 441 交接接口。
- **升级条件**：车端 Python 2/Catkin 回归失败、补充路线出现规划失败，或边界格动态障碍表现异常时，停止部署并重新审查路线守卫与代价地图策略。
