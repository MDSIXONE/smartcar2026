# 犯错档案（2026-08-04）

> 按日期拆分的错误记录，索引见《索引.md》。
### 2026-08-04：到点 OCR 将一圈扫描错误地当成单次候选

- **现象**：代码在原地转圈拿到第一条高置信 OCR 后立即结束扫描，最终又按墙点编号而不是
  `日用品/食品/电子产品` 三类去重；因此既不能在一圈内收集三类，也不能满足类别结果的任务语义。
- **原因**：异步 OCR 回调只实现了“返回首条候选”的接口，墙点编号被误作结果身份，而没有独立
  的类别白名单和完整转圈状态机。
- **修复**：一圈扫描改为候选事件循环：只有未保存的三类文本才停车、居中、测距和记录，处理后
  恢复抓拍朝向并完成剩余角度；最终按类别去重。墙位置改为同时间戳激光前向射线与已知墙边界的
  交点，并要求实际测距一致。
- **预防**：涉及“同一运动周期多个感知结果”的需求，必须测试重复类别、三个不同类别、处理暂停
  和总旋转进度；结果身份必须来自业务类别，不能借用空间编号。

### 2026-08-04：车端构建命令的跨 Shell 引号解析失败

- **现象**：首次通过 PowerShell SSH 执行车端构建时，嵌套的 `bash -lc`、`$()` 和 `awk` 引号在
  远端解析为不完整命令，于语法检查阶段退出。未开始构建、未启动 ROS、未发布车辆命令。
- **原因**：把三个 Shell 的变量/命令替换嵌入同一命令字符串，转义边界不可验证。
- **修复**：改为 PowerShell here-string 经标准输入交给远端 `bash -s`，从而保持车端脚本原样。
- **预防**：Windows 到 Bash 的多行构建/诊断脚本禁止嵌套 `bash -lc` 字符串；使用标准输入或上传的
  脚本，并把网络变量在所有 `source` 之后明确导出。

### 2026-08-04：PowerShell 标准输入将 CRLF 传给车端 Python 2 测试

- **现象**：修正引号后，车端 `catkin_make --pkg ucar_2026` 已成功，但 here-string 经 SSH 管道传递
  的测试参数含 CRLF，Python 2 的 `unittest` 将 `-v\r` 解析成无效选项。未启动 ROS 或车辆。
- **原因**：PowerShell here-string 默认使用 Windows 行结束符，`bash -s` 对脚本行可容忍，但该行末参数
  仍可传入 Python。
- **修复**：构建结果保留；测试改为独立、无 here-string 的远端 Python 2 调用。
- **预防**：经 Windows 标准输入传递 Linux 脚本时，测试参数不要置于末行；更稳妥的是将构建和单测
  分成独立远端调用，并检查参数字节而不是仅检查 Shell 是否成功。

### 2026-08-04：Python 2 对中文类别排序发生 ASCII 编码错误

- **现象**：车端 Python 2 回归在 `select_three_processing_observations()` 排序中文类别时抛出
  `UnicodeEncodeError`；本机 Python 3 回归未暴露此问题。没有启动 ROS 或车辆。
- **原因**：排序键把 Unicode 类别名显式转换为 `str`，Python 2 默认按 ASCII 编码。
- **修复**：排序键保持 Unicode 值，不进行 `str()` 转换；测试覆盖三类中文去重。
- **预防**：车端仍为 Python 2 的模块，任何中文字符串处理都必须在 Ubuntu 18.04 上执行回归；本机
  Python 3 通过只能作为纯函数初检，不能代替部署验收。

### 2026-08-04：隐藏启动 WSL Master 时未将 Bash 命令作为单一参数

- **现象**：首次用 Windows 隐藏进程启动 `start_ros_master.sh` 后，20 秒内 11311 未监听；小车未
  启动。前台限时诊断证明 Master 脚本本身可在 `192.168.8.199` 正常启动。
- **原因**：`Start-Process -ArgumentList` 把 `bash -lc` 后的命令拆成多个 Windows 参数，Bash 没有
  获得完整启动脚本字符串。
- **修复**：以一个带引号的 Bash `-lc` 命令参数启动，再通过 ROS API 核验监听后才允许车端连接。
- **预防**：后台启动 WSL/Bash 时，要先验证 `-c` 命令整体作为一个参数传递；不得把“进程已创建”
  当作 ROS Master 已就绪的证据。

### 2026-08-04：实车 OCR 居中误差在点 25 未收敛

- **现象**：任务安全门通过后，动态守卫安全跳过 12/23/14，25 到达误差 `0.030 m`。OCR 识别到
  “日用品加工车间”，但重拍居中误差大多为约 `-176 px`；一次校正后暂为 `+45.6 px`，下一次又回到
  `-176 px`。任务按“误差向反方向放大”保护中止，未输出任何类别/墙交点。
- **原因**：当前实测表明 OCR 框中心与受保护的小角度转向之间没有稳定的单调关系；可能是镜像符号、
  异步帧/位姿延迟或场景中文字框切换。不是 OCR 未读到文本，也不是前向墙射线逻辑触发。
- **修复**：本轮中止后先由停止脚本发布零速并停止所有进程。后续修正使 OCR 居中直接以受限
  `cmd_vel` 转动，并用 `odom → base_link` 的实际 yaw 增量确认完成；镜像帧会反转控制符号，不再让
  `move_base` 的同位置目标代替原地转向。
- **预防**：下次先离线比对该运行目录的每张重拍图、bbox、镜像方向和 capture yaw；在不移动实车的
  mock/回放中验证居中正负号与重拍稳定性后，才允许再次实测。不能因识别到文字而绕过居中保护。

### 2026-08-04：PD 车端回归命令再次被 PowerShell 解析

### 2026-08-04：镜像 OCR bbox 被重复反转，PD 把目标越转越偏

- **修复**：PD 直接使用 helper 输出 bbox 的符号，移除第二次镜像反转；保持 odom 实测 yaw 门。
- **预防**：摄像头镜像的控制符号必须以实际“命令 yaw → 下一帧 bbox”闭环证据判定，不能仅按原始图像
  的几何直觉推断。首次实测应记录至少两步误差和实际 yaw 后再放开完整扫描。

### 2026-08-04：PD 居中末段在 deadline 边界误中止

- **现象**：第四次实车到达点 25 后，“日用品加工车间”的 bbox 误差已从 `-181.4 px` 连续收敛到
  `-33.0 px`。最后一次小角度校正要求 `0.039 rad`（有效阈值 `0.029 rad`），但控制 deadline 到达后
  直接中止，未保存类别/墙边界结果。
- **原因**：`rotate_in_place_for_yaw` 的超时分支只发零速后即抛出异常，未等待底盘停止并补采最后一帧
  odom。离散里程计在 deadline 前后跨过阈值时会被误判为失败。
- **修复**：deadline 后先零速、确认连续低速 odom，再把最终有向 yaw 增量计入进度；仍未达既有阈值才
  中止，并在错误中记录 `actual`/`required`。不放宽 yaw 容差，不在 deadline 后继续发布转动命令。
- **预防**：原地转向的 timeout 路径必须与成功路径一样有停车确认和最终传感器采样；正/反方向和
  “补采仍不足”都必须纳入 Python 2 车端回归。

### 2026-08-04：冷启动复测被 IMU 失活安全门阻断

- **现象**：用户重新放回起点后的全量冷启动中，任务未通过安全门，连续报告
  `Imu sensor not active any more`；未发送任何到点行驶命令。
- **对比**：此前一次启动在安全门通过后出现 `/odom_raw is stale by 0.410 s`；本次没有重现该断流，
  而是更早暴露出 IMU/里程计链路失活，因此目前不能把 odom 超时判断为必然复现。
- **处理**：停止脚本已先发布零速度并关闭车端 launch，随后关闭 WSL ROS Master。静止诊断时
  `/odom_raw` 为有限值、约 20 Hz，最大观测间隔 `0.152 s`，但这不能替代启动期 IMU 有效性检查。
- **预防**：当安全门出现 IMU 失活、`NaN`、`TF_NAN_INPUT` 或 odom stale 时，必须先完整重启导航/
  底盘里程计链路，重新确认有限 `/odom_raw` 与两段 TF；不得自动绕过该门或放宽 stale 阈值。

### 2026-08-04：原生 OCR 启动窗口再次触发 odom stale

- **现象**：下一次冷启动通过安全门（111 个有限 odom 样本和两段 TF）、到达 52（误差 `0.027 m`）并
  完成 QR `a → d → i`。在发布 `OPEN_ROS_IMAGE_OCR`、尚未输出 `PRODUCTION_NATIVE_OCR_READY` 的
  约一秒窗口内，任务报告 `/odom_raw is stale by 0.448 s` 后中止。
- **结论**：该 stale 可复现，但不是固定在起点到 52 或 IMU 门的单一位置；与原生 OCR helper 启动窗口
  时间相关。尚未证明是 Python 任务回调、helper 启动 CPU 竞争还是底盘发布链路抖动，不能把相关性当作
  已确认根因。
- **处理**：异常路径已关闭相机/OCR；停止脚本发布零速度并关闭车端 launch，随后关闭 WSL Master。
- **预防**：后续修复需先用时间戳区分“底盘没有发布 odom”和“任务节点没有收到 callback”，再决定是否
  对 OCR 启动异步化、降低启动负载或调整安全检查；不得仅为通过 OCR 启动而放宽 `odom_timeout`。

### 2026-08-04：底盘驱动忽略串口短读的实际返回长度

- **现象**：`robot_pose_ekf` 在任务 OCR 启动前后均记录约 `1.02 s` 的 wheel odometry 间隔；静态
  OCR helper 启动时 `/odom_raw` 仍可约 20 Hz，说明“任务 Python/GIL 卡住”不能解释全部断流。
- **原因**：`base_driver` 原先忽略所有 `serial_.read()` 的返回字节数。字段短读时，旧缓冲残留仍可能
  参与 CRC 和帧解析，造成失步或错误地延后下一帧有效里程计。
- **修复**：所有底盘与 IMU 字段改为读满才解析；短读清空缓冲、丢弃帧并重新找帧头。字段总读取预算
  用单调时钟限为 `serial_timeout`（默认 50 ms）加最多一次底层读超时，避免每次仅返回少量字节时无限
  阻塞；新增短读与真实 odom/IMU 发布间隔日志。保持任务 `0.35 s` 安全门，不伪造或重发 odom。
- **预防**：车端静态验证必须检查 `BASE_SERIAL_RESYNC_SHORT_READ` 和
  `BASE_*_PUBLISH_GAP`。若仍出现短读，先零速停止并检查 CP2102、串口线束、公共地、供电和 MCU
  发帧，不能通过放宽 OCR 或 odom 超时掩盖硬件/字节流故障。

### 2026-08-04：Melodic 环境脚本与 `set -u` 不兼容

- **现象**：车端准备构建 `ucar_controller` 时，在 `source /opt/ros/melodic/setup.bash` 前启用
  `set -u`，Melodic 的 `1.ros_distro.sh` 读取未定义 `ROS_DISTRO` 并立即退出；未构建、未启动 ROS、

- **原因**：ROS Melodic 的环境钩子假定未定义的环境变量可展开为空，与 Bash nounset 不兼容。

- **预防**：所有小车端构建、诊断和停止脚本都不得在 source ROS 环境之前启用 nounset；必须同时保持
  `ROS_MASTER_URI` 与 `ROS_IP` 在每个 `source` 之后重新设置。

### 2026-08-04：小车 Catkin 子包构建规则陈旧

### 2026-08-04：车端 Catkin 白名单排除了底盘驱动

- **现象**：强制重新生成后仍只有 `cym_planner`、`jie_ware`、`yolo2025`、`ucar_2026` 四个包进入

- **修复**：临时显式设为 `-DCATKIN_WHITELIST_PACKAGES=ucar_controller` 构建和测试，随后恢复读取到的

- **预防**：在白名单工作区为未列包部署 CMake/测试时，先检查缓存并进行可逆的临时切换；结束前必须
  恢复用户原有构建范围，避免影响后续导航包构建。
