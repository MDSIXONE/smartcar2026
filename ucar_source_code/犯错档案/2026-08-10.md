### 2026-08-10：双物品改造首轮车端单测暴露 3 个测试 mock 缺口

- **现象**：双物品/双类别/仿真联动改造后，车端 `catkin_make run_tests_ucar_2026`
  报告 `80 tests, 3 errors`（均为 test_production_task_geometry.py）：
  ① `test_run_mission_aborts_when_real_item_stops_on_last_leg`——`run_mission` 的
  OPEN_ROS_IMAGE_OCR 分支求值 `self.camera_image_topic`（AttributeError）；
  ② `test_point_mode_is_selected_before_resumed_production_navigation` 与
  ③ `test_qr_completion_does_not_switch_before_first_production_leg`——新方法
  `cruise_production_route` 求值 `len(self.observations)`（AttributeError）。
- **原因**：重构 `run_mission` 时新增了 `observations`/`camera_image_topic` 等读取点，
  但 `ProductionTaskRecenteringPolicyTest` 的 setUp 与个别测试没有补初始化这些
  属性——与 08-07「车端单测暴露测试缺口」同根因：**改动节点行为后没有同步检查
  相关测试的 mock 状态**。
- **修复**：两个测试类的 setUp 补 `self.task.observations = []`；
  `test_run_mission_aborts_when_real_item_stops_on_last_leg` 补
  `self.task.camera_image_topic = "/usb_cam/image_raw"`。生产代码未动。
  修复后车端全量 `80 tests, 0 errors, 0 failures, 0 skipped`。
- **预防**：凡新增/重构 `run_mission` 直接引用的实例属性（尤其被 mock 测试覆盖的
  路径），必须先在测试 setUp 里与既有 mock 属性同步补齐；车端全量测试是唯一权威
  验收（本机 Python 3 下任务类测试会整类 skip，无法提前暴露）。

### 2026-08-10：WSL2 会话退出关闭发行版，后台 roslaunch 被连带杀掉

- **现象**：`wsl -e bash -c "... nohup roslaunch car3 task3_prepare.launch ... &"`
  启动仿真环境后，命令返回、会话结束，roslaunch/gzserver/rosmaster 全部退出；
  master 日志尾部出现 `keyboard interrupt, will exit` / `signal_shutdown [atexit]`。
- **原因**：WSL2 默认在最后一个 `wsl` 会话退出后关闭发行版，`nohup` 只能防
  SIGHUP、防不了发行版整体关闭；后台进程树被连带终止（与仿真环境本身无关——
  无界面模式 spawn 锥桶、机械臂校准均已完成）。
- **修复**：`C:\Users\<用户>\.wslconfig` 的 `[wsl2]` 段加 `vmIdleTimeout=-1`，
  然后 `wsl --shutdown` 重启 WSL 生效；用跨会话 `sleep` 后台进程验证持久存活。
  不能改配置时启动命令必须 `setsid nohup ... < /dev/null &` 脱离会话。
- **预防**：WSL 后台长任务（roslaunch、bridge、服务）先确认发行版常驻配置，再
  继续联调；诊断时先看 master/roslaunch 日志末尾（`keyboard interrupt` 即会话
  关闭信号）。

### 2026-08-10：arm_initial_pose_ready 话题随节点退出而注销，不能作就绪信号

- **现象**：bridge 按 TASK3_RUNBOOK 轮询 `/sim_task3/arm_initial_pose_ready`，
  机械臂校准日志已出现 `calibrated initial arm pose applied smoothly`，但
  `rostopic echo -n 1 /sim_task3/arm_initial_pose_ready` 一直无数据、
  `rostopic info` 报 `Unknown topic`。
- **原因**：`set_arm_initial_pose.py:334` 发布一次 `Bool(True)`（latch）后，
  因 launch 里 `hold_initial_arm_pose=false` 直接退出（无 rospy.spin），
  节点注销时话题从 master 移除，latch 消息随之消失。
- **修复**：bridge 就绪判定改为轮询**常驻**的 `/map` 话题（map_server 全程
  发布，prepare 期间必在）；`rostopic echo -n 1 /map` 非空即就绪。
- **预防**：用「一次性发布后即退出的节点话题」做外部就绪信号前，先实测该话题
  在节点退出后是否仍可订阅；优先选择常驻发布者（map_server/clock）。

### 2026-08-10：带 GUI 仿真遇 WSLg COPY MODE，`wsl --terminate` 无效需 `wsl --shutdown`

- **现象**：带界面启动 `task3_prepare.launch`（Gazebo + RViz 窗口）后窗口出现
  `[WARN:COPY MODE]` 标题；`/mnt/wslg/weston.log` 出现
  `rdp_allocate_shared_memory: Failed to open "/mnt/shared_memory/..." 
  Input/output error` + `RDP backend: use_gfxredir = 0`，且 `findmnt
  /mnt/shared_memory` 无输出——WSLg 共享内存通道未挂载，退回逐帧复制。
- **处理**（按仿真 FAQ「COPY MODE」章节）：先 `wsl --terminate Ubuntu-20.04`
  重启发行版，检查 weston.log **仍含** `use_gfxredir = 0`（terminate 未恢复
  共享通道）；再执行 `wsl --shutdown`（全停 WSL，Docker Desktop 当时为
  Stopped 无影响），重启后 `grep -c 'use_gfxredir = 0' /mnt/wslg/weston.log`
  归零、`/mnt/shared_memory` 恢复 tmpfs 挂载 → COPY MODE 消失。
- **预防**：WSLg 图形异常优先查 `/mnt/wslg/weston.log` 与 `findmnt
  /mnt/shared_memory`，不要改 Gazebo/RViz 参数；`terminate` 无效时升级
  `shutdown`；恢复后必须复测 weston.log 再启动 GUI 仿真。

### 2026-08-10：run_mission 成功路径 signal_shutdown 污染 nosetests 共享进程

- **现象**：handoff 改造（SUCCEEDED 后 `rospy.signal_shutdown("lane handoff")`）后
  车端全量测试 86 tests 出现 4 errors + 2 failures：camera_stop 参数断言错、
  "did not receive 2 fresh camera frames"、两处 "goal cancellation was not
  acknowledged within 0.5 s"、fresh_qr 返回 None、`MoveBase` object has no
  attribute 'cancel_goal'——且稳定复现（重跑不变）。
- **原因**：nosetests 在同一进程内按字母序跑多个测试类；DualItemTest 的
  cruises 流程测试完整走 run_mission 到 SUCCEEDED 段，真实执行了
  signal_shutdown → rospy 全局 shutdown 标志置位 → 之后 RecenteringPolicyTest
  里所有依赖 `rospy.is_shutdown()` 的循环/分支全部短路（等待循环直接跳过、
  for-else 走真实 cancel_goal 路径撞上 mock 缺方法）。本机 stub 的
  is_shutdown 恒 False 掩盖了该污染。
- **修复**：cruises 流程测试用 try/finally 临时替换 `rospy.signal_shutdown`
  为 no-op（记录事件），finally 恢复；断言追加 "signal_shutdown" 事件
  （顺带锁定交接行为）。production 代码未动（真机行为正确）。
- **预防**：凡新增"run_mission 成功路径"的流程测试，必须先 mock
  signal_shutdown（沿用本修复模式）；改 rospy 全局状态（shutdown/Time 替换）
  的测试要意识到 nosetests 进程内对其他测试类的污染，本机 stub 验证不能
  替代车端 nosetests 实跑。

### 2026-08-10：crc16 反复打断完整任务（第 3~4 次）+ wheelodom TF NaN

- **现象**：多轮全流程中任务反复在运动/等待阶段因 `check crc16 faild(ahrs/imu)` 安全中止
  （本日第 3~4 次）；另一次启动后车不动，日志出现
  `TF_NAN_INPUT: Ignoring transform for child_frame_id "wheelodom" ... nan value` +
  `move_base unavailable after 90.0 s`（重启小车后恢复）。
- **原因**：crc16 为底盘串口/AHRS 数据 CRC 校验失败——与 08-07 的
  `usb 1-2.1`（Terminus Hub）枚举失败/串口链路问题同源，属**硬件链路问题**；
  wheelodom NaN 为底盘里程计启动期/链路瞬时 NaN（AGENTS 规则警告项）。
- **处理**：安全门按设计触发（任务自动停止、发布零速度、清理）；换电池/重启小车
  可短暂恢复但未根除；dmesg 仅启动期有 usb_suspend 记录，运行期无新枚举风暴证据。
- **预防**：crc16/NaN 反复打断时优先物理排查 USB Hub 与 CP2102 线缆/接口；
  按规则出现 TF_NAN_INPUT 必须先重启底盘链路、确认 /odom_raw 有限且
  odom->base_link、map->base_link TF 恢复后才能继续。
