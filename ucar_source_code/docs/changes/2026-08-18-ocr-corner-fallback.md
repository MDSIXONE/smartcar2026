# 守卫拦截后的四顶点替代 OCR

## 行为

当分组 OCR 主路线的逻辑中心点被动态守卫拦截时，任务不立即忽略该中心点，而是读取该点四个守卫顶点的最新扫描状态：

1. 排除当前扫描已命中的顶点；
2. 按固定编号顺序导航到剩余顶点之一，但逻辑目标仍保持原中心点；
3. 备用导航继续监控剩余候选顶点；若备用点也被新障碍命中，则尝试下一个候选；
4. 四个顶点都不安全时，才将原中心点记为 `ignored` 并进入分组调度的下一步。

备用顶点完成导航后仍执行原中心点的 360° OCR、墙面观察和类别记录，因此不会改变类别停车流程。规划失败、里程计/TF 异常或守卫扫描失效仍直接中止任务，不被当作“换一个点”吞掉。

## 涉及文件

- 三套 `ucar_2026*/scripts/production_task_2026.py`：支持逻辑目标与实际备用导航点分离、守卫点覆盖监控、备用点重试；
- `docs/debug-rviz-observation.md`、`docs/operations.md`：现场行为说明。

- 三套几何测试通过：标准 `90` 项、国赛 `91` 项、额外 `105` 项（ROS 缺失测试按现有测试约定跳过）；
- 三套任务脚本 Python AST 语法检查通过；
- 替代点审计通过：初始候选 `[420,428,429]` 中 420 再次被守卫命中时，按顺序继续尝试 428；
- 三个 `2026.launch` XML、五组默认路线和 `git diff --check` 通过；
- 已通过动态解析的 `ucar-mini` 地址部署 11 个运行文件；车端 Python2 语法、4 个 launch XML
  和 11 个文件的 SHA-256 校验通过，未启动 ROS 或车辆运动。

## 已知限制

四个守卫顶点是备用 OCR 观察位置，实际可导航性和 OCR 视角仍必须在车端 Ubuntu 18.04 / ROS Melodic 环境低速验证。启动前仍需确认 `/odom_raw`、`odom -> base_link`、`map -> base_link`、`/scan` 和零速安全门。
