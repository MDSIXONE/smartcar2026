# alt3：转圈 OCR 入口门槛改为“合并或任一簇达标”

## 目的

审计“360° 扫描同帧出现两块牌”的处理时发现最后一处残留：进入候选流程的
门槛（置信度 ≥ ocr_scan_candidate_confidence=60、面积 ≥ 1000px²）仍只看
helper 的**全帧合并**检测。两牌同框时 classify 作用在拼接文本上可能打出低
分，导致整帧被丢弃——即使其中一块牌单独看足够强。若两牌角距很小、各自
“单独可见”的弧很窄，理论上存在连续丢帧窗口。选簇循环本身没有此问题
（第一候选被 handled/rejected/已记录挡掉会落到下一候选，不会整帧作废）。

## 改动

仅动 `ucar_2026/scripts/production_task_2026_alt3.py`（diff：新增 1 个纯函
数 + 2 处调用替换，共 +37/-2 行）：

- 新增模块级纯函数 `any_production_cluster_candidate(response, min_conf,
  min_area)`：合并检测达标，**或**任一按牌聚出的簇（文本非空、簇均值置信
  ≥ 门槛、簇面积 ≥ 门槛）达标，即放行进入选簇候选流程；helper 无逐框
  items 时回退为原合并判定，行为与旧版一致。
- `rotate_full_revolution_for_ocr` 的两处入口判定（转圈中、收尾最后一帧）
  由 `is_navigation_ocr_candidate` 换为上述函数；其余逻辑不变。

launch 无新增参数；alt1f/alt2f 与所有既有文件零改动。

## 验证

- `python3 -m py_compile` 通过；生成器锚点断言全部唯一命中。
- 纯函数单测 4 例：双牌同框且合并置信 42（<60）但单簇 90 → 放行；
  合并本身达标 → 放行；仅低置信噪声簇 → 拒；无 items 且合并不达标 →
  维持旧行为拒。
- diff 审计仅上述 3 处；未实车运行。

## 同帧双牌处理的完整审计结论（随本次记录）

1. 目标牌与另一块牌同帧：候选按“簇置信度、离画面中心”排序逐个过四道
   跳过检查，第一名被挡会落到下一名——不会因出现另一块牌而整帧作废
   （旧 union 代码确有此缺陷：合并文本归到被挡类别即 return False，另一
   块牌陪葬；08-21 的选簇循环已修）。
2. 对准过程中另一块牌入画：对准每帧只取目标类别所在簇，误差信号不受
   干扰；另一块牌的任何状态（handled/rejected/seen）不会被误标。
3. 同帧只处理最优一块，另一块由后续帧兜住：0.2 s 一拍 ≈ 每 4° 一帧，
   单块牌可见弧数十度，且现在整圈转满，必然再次成为候选；已处理类别
   进入 handled_categories 不会重复抢占。
4. 既有小折扣（各变体皆然，未改动）：对准把车头拉离扫描弧后，续转从新
   朝向补满剩余角度，极端情况下圈尾有 ≤ 对准转角（约十几度）的方向缺少
   二次覆盖；因捕获密度高、牌面可见弧宽，实践中不构成漏检，记录备查。
